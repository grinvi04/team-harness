# 혼자 개발하며 공통 업무 진행하기

Team Harness는 한 개발자가 LLM으로 백엔드·프론트엔드·DB·인프라 업무를 수행하면서 기술 기준·설정·검사
절차를 재사용하고, 실제로 도움이 된 구성을 동료에게 확산하는 기반이다.
Agent Orchestration에서는 **필요한 인계·검증·재개 원칙만** 가져왔다.
별도 개발 도구 패키지나 역할 체계를 설치하지 않는다.

의존 변경을 여러 PR로 나눌 때는 선택형 [층별 개발 안내](stacked-development.md)의 명령·복구 경계를 따른다.

## 자연어 요청과 역할 분담

“주문 취소 기능을 추가해줘”, “목록 오류를 고쳐줘”처럼 결과를 요청한다. 스킬 명령은 선택 사항이며
에이전트가 프로젝트 지침과 실제 요청으로 적절한 방법을 선택하고 현재 단계를 짧게 알린다.

| 책임 | 담당 |
| --- | --- |
| 일반 요구 정리·설계·TDD·디버깅 | 사용자가 선택한 방법론 하나. 설치된 Superpowers 활용, 미설치면 native 방식 |
| 기술 기준·설정·검사 연결 | Team Harness + 제품의 AGENTS.md·검사 명령 |
| 인계·현재 후보 검증·GitHub delivery 조건 | 해당 Harness 계약, 기존 제품 기록·서버 gate |
| 제품 코드·수용 기준·현재 진행 | 제품 저장소 |

Harness의 plan·feature-add·feature-modify·systematic-debugging은
[공통 프로젝트 계약](../../plugins/harness-guard/skills/ao-coordinate/project-contract.md)을 읽고 위 역할에 연결한다.
에이전트가 시험 전에 [QA 범위·완료 기준](../ai-collaboration.md#qa-범위와-완료-기준)을 요구·위험에서
구체화하고 직접 검증한다. 사용자의 최종 승인 책임이 테스트 실행·오류 발견을 대신 맡는다는 뜻은 아니다.
일반 방법론에서 만든 계획·재현·테스트를 다시 만들거나 별도 승인을 반복하지 않는다. 새 feature 브랜치의
스펙 위치·테스트 잠금·필수 독립 검증·PR/CI/사람 승인 조건은 유지한다. 방법론 설치 자체가 필수는 아니다.

- “기능을 설계해줘”: 일반 설계 방법으로 요구를 정리하고 프로젝트 계획 계약에 연결한다. 계획만 요청이면 구현하지 않는다.
- “오류 원인만 확인해줘”: 진단 방법과 프로젝트 재현 증거를 사용하고 파일을 수정하지 않는다.
- “승인한 기능을 구현해줘”: 기존 계획에서 구현하고 제품 검사·완료 조건으로 인계한다.
- “머지해줘”: 방법론을 다시 시작하지 않고 현재 PR의 리뷰·CI·승인 조건을 확인한다.

자동 선택은 플랫폼이 수행한다. 기본 설치에는 `UserPromptSubmit` 의도 분류를 연결하지 않는다.
선택이 맞지 않으면 사용할 스킬을 명시한다. 자동 선택과 명시 호출은 실제 적용·결과로 각각 확인한다.

## 개발자가 하는 일

### 처음 연결할 때

기존 제품 저장소를 Codex에서 열고 아래 **첫 확인 요청**을 보낸다. 이미 준비됐다면 바로 업무를 맡긴다.

```text
이 저장소에서 혼자 개발하면서 Team Harness를 사용하려고 해.
AGENTS.md, 코드 구조, 작업 중인 변경, 브랜치 방식, 로컬 검사·CI와 Harness 적용 상태를 확인해줘.
기존 설정·작업·브랜치 흐름을 보존하고, 이미 연결된 구성은 재사용해.
전체 템플릿이나 Git Flow를 일괄 적용하지 말고, 개발 시작에 빠진 필수 연결만 찾아줘.
파일·설정을 변경하지 말고 지금 시작 가능한지, 준비가 필요하면 무엇을 왜 바꿔야 하는지,
이 저장소에서 사용할 구현·검사·리뷰·PR 흐름을 간단히 정리해줘. 확인과 미확인을 구분해.
```

제품 저장소에서 시작한다. AGENTS.md에 제품 구조·스택·실제 검사 명령·브랜치 방식·유지할 계약과 기록
위치를 정하고 기존 설정을 재사용한다. 신규 연결은 [온보딩](../onboarding.md), 기존 repo의 선택 적용은
[선택형 온보딩](existing-repository.md)을 따른다. 셋업 명령과 정책 변경 절차는 두 정본에만 둔다.
검사는 [스택별 연결](../onboarding.md#스택별-검사를-연결하는-방법)을 따른다. 준비된 지원 스택 앱은
[로컬 검사 진입점](../local-development.md)을 선택할 수 있다. 제품 명령과 CI가 같은 검사를 실행해야 한다.

요청에는 **목표·유지할 것·완료 기준·진행 범위**를 적는다. 에이전트는 부족한 검사 조건을 현재 코드에서
구체화하고 중요한 미결정만 묻는다. 브랜치·스펙은 제품 규약에 맞추며 기존 승인 계획을 다시 만들지 않는다.
로컬 전용 제품은 아래 PR·CI·원격 병합 단계를 적용하지 않고 로컬 검사와 제품 기록으로 마친다.
GitHub 사용 여부와 별개로 실패·미실행을 그대로 보고하고 구현·병합·배포 완료를 구분한다.

### 혼자 개발할 때

준비가 되면 아래 **업무 시작 요청**의 대괄호를 실제 업무로 바꾼다. 필요한 연결 변경은 따로 범위를 정해 맡긴다.

```text
[개선하거나 해결할 실제 업무]를 진행해줘.
목표: [얻어야 할 결과]
유지할 것: [기존 동작·호환성·업무 규칙]
완료 기준: [관찰하거나 시험해서 확인할 결과]
현재 코드와 프로젝트 지침에서 범위와 검사 방법을 구체화하고,
필요한 설계·구현·검증·독립 리뷰·PR 생성까지 진행해. 관련 안내·진행 기록도 갱신해.
이미 충족한 조건은 반복하지 말고 중요한 미결정만 질문해. 병합·배포는 별도로 요청할게.
실패하거나 실행하지 못한 필수 검사는 완료로 처리하지 마.
```

아래 표는 결제 전 주문 취소·예약 재고 복구를 예로 든다. 중복·동시 취소의 복구는 1회, 기존 생성·조회는 유지한다.
main 중심이면 `작업 브랜치 → main PR`로 진행한다. 여러 작업을 모아 출시하려면 제품이 선택한
`작업 브랜치 → develop → release → main → develop 역병합` 흐름을 사용한다.
스킬 이름 대신 목표를 요청해도 에이전트가 해당 프로젝트 계약과 절차를 연결한다.

| 단계 | 할 일 | 단계별 완료 기준 |
| --- | --- | --- |
| 요구·설계 | 상태·재고·실패 계약과 변경 범위를 기존 스펙/이슈에 연결 | 취소 허용·거부·중복/동시 요청의 기대 결과와 검사 방법이 정해짐 |
| 구현·검사 | 작업 브랜치에서 구현하고 제품의 변경·유지 검사 실행 | 정상 취소·거부·재고 1회 복구·기존 생성/조회가 통과하고 필수 품질 gate 성공 |
| PR·검토 | 셀프 리뷰 후 독립 Codex 리뷰·지적 처리·현재 PR CI 확인 | 현재 head/base의 검토 완료, 미해결 차단 지적 없음, 기존 승인·필수 CI·외부 상태 조건 충족 |
| 병합·정리 | 승인된 대상 브랜치에 공식 래퍼로 병합 | 원격 MERGED·실제 SHA 확인, 보호 보존, 로컬 최신화와 브랜치 정리 결과 확인 |
| 출시·배포 | 요청 범위에 포함되면 제품의 release-check와 release/배포 절차 수행 | 검증 후보·main/태그·배포 대상이 연결되고 해당 환경 상태 확인; 미배포는 구분 |
| 기록·인계 | 관련 현재 안내와 다음 행동을 제품 기록에 반영 | 변경 이유·현재 후보·검사 결과·남은 문제·다음 행동을 같은 기록에서 찾을 수 있음 |

DB·인증·실제 저장이 핵심인 검사는 승인된 비운영 환경에서 실제 경계를 관찰한다. 목 응답·렌더 스모크로
재고 정합성이나 권한을 확인했다고 보고하지 않는다. 환경이 없으면 해당 필수 검사는 UNVERIFIED다.
PR·리뷰·병합의 명령과 판정은 [리뷰 내용 기준](../code-review.md)과
[리뷰 게이트 절차](../../plugins/harness-guard/skills/pr-review-gate/SKILL.md)가 정본이다.
solo-merge는 같은 기준의 개인 solo 예외가 필요할 때만 선택한다. CI·독립 리뷰를 대신하지 않는다.

```text
이 PR을 기존 리뷰·CI·보호 조건을 유지하면서 main에 병합해줘.
병합 결과와 로컬 최신화·이번 작업 브랜치 정리까지 확인해줘.
```

병합 대상은 제품에서 선택한 main 또는 develop으로 바꾼다. 이미 병합까지 승인한 작업은 다시 승인받지
않고 이어간다. 태그·설치·배포도 맡길 때는 대상과 완료 기준을 요청 범위에 함께 적는다.

### 작은 팀에서 사용할 때

각자 AI를 쓰면서 공유 기록과 담당 범위를 연결하는 [팀 사용 가이드](team-development.md)를 따른다.
첫 준비 확인 → 공유 업무 계약 → 담당자별 작업 → 독립 리뷰 → 합친 상태 검증 → 병합·인계 순서다.
복사용 첫 확인·업무 시작·통합·인계 요청과 단계별 완료 기준은 그 문서에 둔다.

### 기능 개발 외 업무

같은 흐름에서 산출물과 완료 기준만 해당 업무에 맞춘다. 진단·설계만 요청했으면 수정·PR로 이어가지 않는다.

| 업무 | 바로 쓸 요청 예시 | 완료 기준 |
| --- | --- | --- |
| 설계 검토 | “주문·재고 책임 경계의 문제와 최소 대안을 비교해줘. 수정하지 마.” | 현재 코드 근거·대안의 영향/비용·결정할 사항 제시 |
| 오류 진단 | “목록 새로고침 실패를 재현하고 원인을 찾아줘. 진단만 해.” | 원래 증상의 재현 결과·실패 증거·확정 원인과 미확인 가설 구분 |
| 리팩터링 | “조회와 표시 로직을 분리하되 응답·화면 동작은 유지해.” | 요청한 구조 변경과 유지 계약의 회귀 검사·필수 품질 gate 통과 |
| CI 개선 | “로컬 실패를 CI가 놓치는 원인을 확인하고 검사 연결을 고쳐줘.” | 안전한 실패 예제가 로컬·CI에서 실패하고 정상 예제는 통과 |

기능 예시와 표는 업무 실행 결과가 아니다. 제품의 실제 명령·필수 검사를 연결해 현재 후보에서 판정한다.
실패·미실행·자동 판정 불가를 제품 기록에 남기며 상세 로그를 별도 중앙 상태로 복제하지 않는다.

## 필요한 구성만 유지

| 구성 | 책임 |
| --- | --- |
| 기존 Harness 문서·workflow | 기술 기준, 계획·구현의 프로젝트 계약과 PR·리뷰·릴리즈 절차 |
| [ao-coordinate](../../plugins/harness-guard/skills/ao-coordinate/SKILL.md) | 단계 사이의 인계·재개와 현재 증거 연결 |
| 제품 저장소·GitHub | 코드, 요구사항, 결정, 실제 진행과 검증 기록 |
| 현재 실행 플랫폼 | 역할 실행과 도구 권한·중단 |

`ao-coordinate`는 기존 workflow-pack의 선택 skill이다. Codex에서는 현재 에이전트가 요구·테스트 계약 검수와
Git 통합·최종 인수를 담당한다. 명확한 저위험 구현과 독립 조사·검토는 [native 실행 계약](../../plugins/harness-guard/codex/native-runtime.md)
안에서 기존 역할에 위임할 수 있다. 모델은 [승인된 실행 설정](../model-tiering.md)을 따른다. core는 이 skill에 의존하지 않는다.
일반 위임을 기술적 권한 집행으로 주장하지 않으며, 실제로 필요한 권한·독립성 조건은 그대로 확인한다.

초기 통합본의 npm 패키지, JSON schema·검사기, 작업 기록 생성 CLI와 장문의 역할·상태 계약은 제거했다.
선언을 서로 비교하는 검사만으로 실제 권한이나 품질을 확인할 수 없고, 현재 제품 흐름에 별도 API가 필요하지 않기 때문이다.
현재 조정에는 npm 설치, Task/Assignment/Artifact 작성, 역할 profile 복사가 필요 없다.

## 초기 통합본에서 전환

`team-harness-orchestration` 또는 이전 `agent-orchestration-contracts`를 설치했다면 먼저 제품에서 실제 호출부와
수정된 관리 파일을 확인한다. 현재 안내를 기존 제품 지침에 연결하고 불필요한 의존성·설치 명령만 제거한다.
다른 용도가 있는 package.json이나 사용자가 수정한 파일은 지우지 않는다. 관리 profile이 남은 이전 설치는
그 설치 버전의 hash 확인 제거 절차를 검토한 뒤 처리하며, 출처가 불분명하면 덮어쓰거나 삭제하지 않는다.
제품의 과거 작업 기록·JSON 증거는 이력으로 보존한다. 과거 시험의 예외를 새 작업에 적용하지 않는다.

## 릴리즈 검사와 실행

공용 release-check는 제품 AGENTS.md가 선언한 품질·보안·DB·추가 검사를 현재 후보에서 판정한다.
생성물 검사·changelog·외부 원본 경로는 제품이 선언한다. 필수 검사 누락과 접근 실패는 NO-GO다.
release는 검증 후보의 main PR·태그·develop 역병합·정리를 증거별로 기록한다.
서버 없는 제품의 health는 SKIP이며 태그 발행을 설치·배포·운영 정상으로 보고하지 않는다.

회사 도입은 기존 계획·승인·검사와 [선택형 온보딩](existing-repository.md)을 연결한다.
실제 독립 작성자·리뷰어의 업무 인수는 [회사 인수 계약](../company-acceptance.md)에 따른다.
