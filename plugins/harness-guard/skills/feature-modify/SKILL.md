# feature-modify — 기존 동작 변경의 프로젝트 연결

일반 구현·TDD는 선택한 Superpowers의 test-driven-development/실행 스킬 또는 native 방법론 하나를 따른다.
먼저 [공통 프로젝트 계약](../ao-coordinate/project-contract.md)을 읽고 현재 변경에 연결한다.
기존 승인·계획·테스트 루프를 다시 시작하지 않는다.

## 변경과 보존의 경계

요청한 새 동작과 그대로 유지할 동작을 구분하고 변경 테스트와 잠글 유지 테스트를 정한다.
원인이 불명확하면 systematic-debugging의 진단 계약을 연결한다. 진단만 요청받으면 수정하지 않는다.
버그 수정은 제품의 fix 규약, 기능 확장은 feature 규약을 따르며 기존 작업 브랜치를 재사용한다.

변경 테스트가 원래 증상 때문에 RED이고 유지 테스트는 PASS인지 확인한다.
검수 뒤 spec/test를 잠그고 관련 코드만 수정한다. 계약 오류는 근거와 함께 정정·재검수한다.
API 의존성을 확인해 순서대로 연결하며 FE/BE를 항상 병렬 또는 순차로 강제하지 않는다.
현재 담당자가 원래 재현·변경·유지 검사와 전체 품질·필수 독립 검증을 확인한다.
완료 증거·문서 현행화·승인된 커밋과 다음 delivery는 공통 계약을 따른다.
