# feature-modify — 기존 동작 변경의 프로젝트 계약

사용자는 바꾸거나 고칠 동작을 자연어로 요청한다. `/feature-modify`는 선택적인 명시 호출이다.
일반 구현·TDD는 선택된 방법론 하나로 수행한다. Superpowers를 사용 중이면 아래 계약을 연결하며
계획·승인·테스트 루프를 다시 시작하지 않는다. 미설치면 native 방식으로 같은 계약을 지킨다.

## 변경 경계 고정

- 실제 제품 루트·AGENTS.md·관련 기술 기준·현재 코드와 호출부·기존 검사·작업트리를 확인한다.
  설치된 API와 제품의 실제 검사 명령을 사용한다. 관련 없는 사용자 변경을 보존한다.
- 요청한 새 동작과 그대로 유지할 동작을 구분하고 변경할 테스트·잠글 기존 테스트를 정한다.
  원인이 불명확하면 `systematic-debugging`의 진단 계약을 먼저 연결한다. 진단만 요청받으면 수정하지 않는다.
- 기존 승인·계획·작업 브랜치를 재사용한다. 버그 수정은 제품 규약의 `fix/*`, 실질적인 기능 확장은
  `feature/*` 등 해당 규약을 따른다. GitHub 하네스의 새 `feature/<name>`에는 승인된
  `docs/specs/<name>.md`가 필요하다. 로컬 제품에 원격·공개·PR을 강제하지 않는다.

## 테스트와 구현의 경계

1. 변경할 동작의 정상·실패·경계 테스트만 추가/갱신하고 유지 테스트는 보존한다.
2. 변경 테스트는 원래 증상 때문에 RED, 유지 테스트는 PASS인지 현재 담당자가 확인한다.
   문법·import 실패나 약한 단언을 기대 동작의 실패로 취급하지 않는다.
3. 검수 뒤 spec/test 계약을 잠근다. 구현자는 이를 수정·삭제·약화·skip하지 않는다. 계약 오류는
   원래 요구와 함께 계약 소유자에게 돌려 정정·재검수하고 조용히 기대값을 바꾸지 않는다.
4. 관련 코드만 수정한다. 위임은 실제 필요·허용 범위와 파일 소유권이 명확할 때만 수행한다.
   실패 재시도에는 새 근거가 있어야 하며, 관련 없는 리팩터링이나 정해진 횟수의 반복을 만들지 않는다.

문서·설정·순수 비주얼 변경은 적합한 내용·구문·연결·화면 검사로 확인한다. 테스트를 절차용으로
만들지 않는다. API 의존성이 있는 변경은 순서대로 연결하고 FE/BE를 항상 병렬 또는 항상 순차로 강제하지 않는다.

## 완료와 delivery 연결

- 변경 동작·유지 동작과 원래 재현 검사를 통과하고 제품의 전체 품질 명령을 확인한다.
- 잠긴 테스트·요청 범위의 diff와 필요한 독립 검증을 확인한다. 실패를 테스트 약화로 해결하지 않는다.
- 관련 로드맵·체크리스트·진행·사용 문서를 실제 결과와 맞추고 과거 증거는 당시 후보로 보존한다.
- `verification-before-completion`에 따라 현재 후보·관련 환경·범위가 같은 증거를 재사용한다.
  변경·드리프트·새 실패·미해결 우려와 gate의 신선도 조건이 있으면 영향을 받는 검사를 다시 수행한다.
- 승인된 Git 범위에서 제품 커밋 규약을 따른다. PR·머지가 승인돼 있으면 `feature-merge`로 이어가고
  리뷰·CI·사람 승인 요건을 유지한다. 로컬 구현을 병합·릴리즈 완료로 확대하지 않는다.
