# 아키텍처·인프라 가이드

[표준 적용 기준](standards-scope.md)을 따른다. 제품의 규모·팀·예산·운영 요구에 맞춰 구성을 선택한다.
특정 업무 도메인, 클라우드, repo 수나 확장 경로를 공통 필수로 정하지 않는다.

## 1. 레포 전략

모노레포와 멀티레포는 변경 단위·권한·독립 배포·공통 코드 관리 비용으로 선택한다.
서비스 수나 Kubernetes 사용만으로 repo 전략을 결정하지 않는다.
앱·인프라·배포 설정의 책임과 변경 검사를 해당 프로젝트에 기록한다.
로컬 작업에 원격 repo 생성·공개·배포를 강요하지 않는다.

## 2. 서비스 아키텍처

운영할 수 있는 작은 구성으로 시작한다. 독립 배포·확장·소유권의 필요가 확인되면 분리를 검토한다.
모듈러 모놀리스는 선택지다. [클린 아키텍처](clean-architecture.md)는 코드 경계의 적용 조건을 설명한다.
모듈별 DB 스키마와 크로스 스키마 조인 제한도 제품의 선택이다.
조회·트랜잭션·데이터 이관 비용을 확인하고, 스키마 분리만으로 보안이나 독립 배포를 보장하지 않는다.

## 3. 배포 설정과 GitOps

배포 후보·설정 변경·실행 결과를 추적할 수 있게 한다. 비밀 값은 Git에 저장하지 않는다.
GitOps는 선언한 상태를 자동으로 맞추는 운영 방식이다. 사용 여부는 배포 환경에 맞춰 결정한다.
[OpenGitOps 원칙](https://opengitops.dev/)과 [Argo CD 안내](https://argo-cd.readthedocs.io/en/stable/)를 참고한다.
Git revert는 코드·설정 변경이다. DB·외부 상태·실제 배포가 자동 복구되는 것은 아니다.
수동 조치는 기존 권한과 장애 절차를 따르고 결과를 선언한 상태에 반영한다.

## 4. 호스팅·배포 대상

관리형 서비스와 직접 운영의 비용·지원 런타임·데이터 위치·복구 요구를 비교한다.
무료 티어, 연결 수, 빌드 제한과 가격은 선택 시 공급자의 현재 자료에서 확인한다.
PaaS에서 VM·Kubernetes로 반드시 이동해야 하는 것은 아니다.
사용할 대상·환경 변수·배포 명령·헬스체크·승인 경계를 프로젝트의 배포 안내에 둔다.

## 5. 인프라·네트워크 표준

- 노출할 서비스와 내부 통신을 구분하고 최소 권한을 적용한다.
- 사람·CI·앱의 접근 자격을 분리한다. 지원되면 짧은 수명의 자격 증명을 사용한다.
- 인증 공급자와 비밀 저장소는 [인증 표준](auth-standards.md)의 계약을 충족하는 것으로 선택한다.
- 환경은 데이터 민감도와 실패 영향에 맞춰 분리한다. 운영 값을 시험 환경에 복사하지 않는다.
- 로그·메트릭·추적·알람은 장애를 판단할 수 있는 범위로 연결한다.
- 백업은 복원 시험으로 확인한다. 코드·설정 이력만으로 데이터 복구를 보장하지 않는다.
- 복구 시간·데이터 손실 허용 범위·책임자를 프로젝트에서 정한다.

AWS를 선택했다면 [AWS Well-Architected](https://docs.aws.amazon.com/wellarchitected/latest/framework/welcome.html)를 참고한다.
이 링크는 AWS 사용을 요구하지 않는다. 공급자별 설정을 공통 표준에 복제하지 않는다.

## 6. 컨테이너 이미지 기준

컨테이너를 사용하는 프로젝트에만 적용한다.
지원 중인 신뢰 가능한 베이스를 선택하고 버전·digest·취약점·CPU·네이티브 라이브러리를 확인한다.
빌드 도구를 분리할 필요가 있으면 멀티스테이지 빌드를 사용한다. 실행 권한과 이미지 안의 비밀정보도 확인한다.
레지스트리 미러는 배포 주체가 바뀌었다는 뜻이 아니다. 특정 JDK 공급자나 레지스트리를 필수로 정하지 않는다.
[Docker 빌드 권고](https://docs.docker.com/build/building/best-practices/)와 선택한 런타임의 공식 이미지를 따른다.

컨테이너 이미지가 같아도 VM에서 Kubernetes로의 전환은 별도 작업이다.
네트워크·저장소·권한·종료 처리·트래픽 전환·복구를 새 환경에서 검증한다.

## 운영 패턴과 한계

외부 호출에는 시간 제한을 둔다. 재시도는 횟수·대기 시간·중복 영향·전체 시간 예산을 정한다.
여러 계층이 각각 재시도하면 부하가 커질 수 있다. 한 요청의 재시도 책임을 정한다.
[AWS Builders’ Library의 재시도 설명](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)은
지수 백오프와 무작위 대기 시간을 다룬다. AWS 전용 기능이 아니라 조건부 운영 패턴으로 참고한다.
쓰기 재시도에는 [API의 멱등성 계약](api-standards.md#기타-규칙)을 함께 확인한다.
