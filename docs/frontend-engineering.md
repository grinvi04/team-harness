# 프론트엔드 설계 판단 안내

[표준 적용 기준](standards-scope.md)을 따른다. 업무·데이터·상태·구조를 설계하거나 바꿀 때 사용한다.
핵심 결과 계약의 정본은 설치되는 [공통 프로젝트 계약](../plugins/harness-guard/skills/ao-coordinate/project-contract.md#프론트엔드-설계-연결)이다.
이 문서는 판단 방법과 사례다. 특정 라이브러리·폴더 체계·그리드·설계 방법론을 필수로 채택하지 않는다.

## 적용과 기록

- 기존 계획·스펙·이슈 하나에 관련 판단과 근거를 남긴다. 별도 중앙 상태표를 만들지 않는다.
- 이미 합의한 업무·구조·QA는 원본을 참조하고 새로 승인받거나 검사 루프를 반복하지 않는다.
- 작은 문구·스타일 수정은 영향 항목만 확인한다. 프론트 없는 작업에는 적용하지 않는다.
- 사용자 업무·화면·상태·API를 함께 조정한다. 아래 순서대로 문서를 모두 작성해야 구현할 수 있는 것은 아니다.
- 기존 구조도 현재 요구와 맞는지 확인한다. 변경할 때는 보존 대상·직접 소비자·비용을 설명한다.

## 업무에서 화면과 구조를 도출

사용자가 어떤 상황에서 무엇을 확인하고 결정하며, 어떤 결과를 만들어야 하는지 쓴다.
메뉴 이름이나 DB 테이블만으로 화면과 컴포넌트를 정하지 않는다.
현재 화면·용어·접근 경로를 확인하고 대표 업무 하나를 조회부터 결과 확인까지 연결한다.
정보·주요 행동·진행 상태·오류 안내의 우선순위와 밀도는 실제 업무와 기존 디자인으로 정한다.
작업 속도나 오류 감소가 목표라면 관찰 가능한 기준을 제품에서 선택한다.

## 값과 상태의 책임

| 구분 | 판단할 것 |
|---|---|
| 서버 확정값 | 어느 응답이 현재 원본이며 저장 뒤 어떤 소비자를 갱신하는가 |
| 편집 초안 | 별도 수명이 필요한가, 취소·재조회·대상 전환 때 어떻게 보존하거나 폐기하는가 |
| 화면 상태 | 검색·선택·확장·탭을 어느 컴포넌트가 소유하며 이동 뒤 복원이 필요한가 |
| 파생값 | 현재 입력에서 계산 가능한가, 서버의 확정·역사 값과 같은 의미인가 |
| 요청 상태 | 저장 중 허용 행동, 오래된 응답·실패·충돌·결과 미확인 뒤의 처리는 무엇인가 |

한 값의 변경 책임과 소비자를 명확히 한다. 모든 상태를 한 저장소로 모으지는 않는다.
원본과 초안의 수명이 같으면 무조건 복제하지 않는다. 취소·독립 편집이 필요하면 분리 이유를 설명한다.
계산할 수 있는 화면 값은 중복 저장을 줄이되 승인 당시 금액 같은 확정 이력을 재계산으로 대체하지 않는다.
응답 유실은 저장 실패의 증거가 아니다. 재시도·중복 방지·동시 편집은 서버 계약을 확인해 연결한다.
화면의 버튼 숨김은 서버의 권한 집행을 대신하지 않는다. 새 서버 기능은 별도 승인 범위로 구분한다.

React의 [상태 구조](https://react.dev/learn/choosing-the-state-structure)·[상태 공유](https://react.dev/learn/sharing-state-between-components)는
상태 책임을 판단하는 자료다. 실제 설치 버전의 동작을 확인하며 다른 프레임워크에 API를 그대로 옮기지 않는다.

## 필요한 책임 경계와 재사용

기존 화면·공통 UI·데이터 접근·업무 규칙과 호출부를 먼저 확인한다.
컴포넌트·훅·모듈을 분리할 때 현재의 복잡성·독립 수명·검사 경계·실제 중복 중 무엇을 해결하는지 설명한다.
단순한 변경은 현재 위치에 둘 수 있다. 새로운 계층·범용 옵션은 예상한 미래 화면만으로 만들지 않는다.
업무 규칙·데이터 연결·화면 조정·표현은 책임을 찾는 관점이며 네 폴더를 생성하라는 지시가 아니다.

시각 요소는 의미가 다른 업무에서도 공통화할 수 있다. 업무 동작의 공통화에는 같은 규칙·실패 처리·변경 이유가 필요하다.
여러 조건 분기로 다른 업무를 억지로 합칠 때는 분리 비용과 비교한다.
회사 공통 그리드·폼·상태 관리가 있으면 해당 계약을 확인한다. 제품에서 필요성이 확인된 경우에 기술 변경을 제안한다.
[코드 경계 안내](clean-architecture.md)는 복잡한 규칙·외부 변경을 분리할 때 선택한다.

## 기존 검증과 연결

디자인 토큰·접근성·실제 화면 확인은 [디자인 표준](frontend-design-standards.md)에 연결한다.
업무·데이터·실패 복구의 기대 결과는 기존 [QA 범위와 완료 기준](ai-collaboration.md#qa-범위와-완료-기준)에 연결한다.
일반 설계·TDD·QA는 선택한 방법론 하나를 따른다. 이 안내로 같은 설계·승인·검증을 다시 시작하지 않는다.
사용 가능한 도구로 승인된 환경에서 검사하고 미실행·미확인은 해당 범위를 그대로 보고한다.
문서 존재·토큰 준수·스크린샷만으로 실제 업무 완료나 저장 결과를 증명하지 않는다.

예를 들어 수량 편집 업무라면 취소의 저장 호출 여부, 저장 성공 뒤 서버 응답 반영,
충돌 시 초안 보존, 목록 선택·검색의 유지가 관련 관찰 경계가 될 수 있다.
제품의 요구가 다르면 기대 결과도 달라진다. 멱등 저장·특정 UX를 모든 업무의 필수 기능으로 추가하지 않는다.

## 전파와 확인 범위

핵심 계약은 plugin 갱신 뒤 새 실행에서 적용 여부를 확인한다. 열린 세션의 목록 갱신을 추정하지 않는다.
소비 템플릿은 신규 셋업에 적용된다. 기존 제품은 자기 지침·회사 정책을 보존하며 필요한 읽기 경로만 별도로 연결한다.
상세 docs 조회가 불가능해도 설치된 핵심 계약은 읽을 수 있어야 한다.
실제 적용 검증은 계약 읽기 로그와 결과의 의미를 함께 확인한다. 한 표본을 모든 실행의 준수나 회사 채택으로 확대하지 않는다.
저장소 반영·패키징·설치·실제 실행·제품 사용성의 검증을 구분한다.
