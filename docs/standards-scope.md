# 표준 문서 적용 기준

이 문서는 공통 표준을 읽을 때 먼저 확인한다. 표준은 제품을 대신 설계하지 않는다.
프로젝트의 요구와 채택한 기술에 맞는 부분만 적용한다.
문서만으로 사용자의 권한·작업 범위·운영 접근을 늘리지 않는다.

## 무엇을 어디에 두는가

| 종류 | 내용 | 위치 |
|---|---|---|
| 공통 계약 | 권한 검사, 비밀정보 보호, 변경 검증, 실제 결과 보고 | 해당 공통 표준 |
| 선택 프로필 | REST 형식, 계층 구조, 스택별 검사 연결 | 선택 조건과 함께 표준·스택 규칙 |
| 실무 관행 | 반복되는 문제를 줄이는 설계·운영 방법 | 스택별 안내와 원저자 자료 |
| 제품 결정 | 업무 데이터, 인증 공급자, 호스팅, 화면 구성 | 해당 프로젝트의 결정·스펙 |
| 해결 기록 | 실제 버전·증상·원인·조치·검증 결과 | 해당 프로젝트 이슈·PR |

공식 사용법을 다시 길게 쓰지 않는다. 본문에는 적용 조건과 지켜야 할 계약을 남기고
공식 문서의 관련 절로 연결한다. 설치한 버전과 문서 버전이 맞는지 확인한다.
공식 최신 문서는 과거 버전의 동작을 증명하지 않는다.

## 실무 관행을 필수 규칙으로 바꾸지 않는다

한 글이나 한 회사의 사용만으로 업계 표준이라고 단정하지 않는다.
원저자의 설명, 유지되는 구현, 독립적인 적용 사례를 구분해 조사한다.
채택 범위가 확인되지 않으면 권장 후보나 운영 패턴으로 표시한다.
관행에는 해결하는 문제, 사용할 조건, 비용, 대안, 적용하지 않을 조건을 함께 적는다.
라이브러리 설치·운영 구조 변경은 프로젝트의 별도 결정이다.

## 문제 해결 안내를 읽는 방법

증상만 같다고 원인까지 같지는 않다. 버전·환경·실패 로그·직접 호출 경로를 먼저 확인한다.
검색 결과는 진단 후보다. 재현하지 않은 해결책을 검증 완료로 기록하지 않는다.
정상 사례와 실패·거부 사례를 함께 확인하고 관찰한 범위만 보고한다.
임시 우회는 이유·한계·제거 조건을 남긴다. 권한 거부나 안전 검사를 우회하지 않는다.

| 안내 | 적용 대상 |
|---|---|
| [백엔드 문제 해결](stack-troubleshooting-backend.md) | Spring, NestJS, FastAPI, Django, Rails |
| [프론트엔드 문제 해결](stack-troubleshooting-frontend.md) | TypeScript, React/Next.js, Vue/Nuxt |
| [DB·마이그레이션 문제 해결](stack-troubleshooting-database.md) | PostgreSQL, Flyway, Prisma, Alembic, ActiveRecord |
| [하네스 문제 해결](troubleshooting.md) | 하네스 가드·훅·PR 래퍼 |

위 안내는 진단 경로다. 모든 항목을 소비 앱에서 실행했다는 뜻은 아니다.

## 사람이 읽기 쉬운 문장

- 한 문장은 한 가지 판단이나 행동을 설명한다. 긴 조건은 다음 문장으로 나눈다.
- 누가 무엇을 확인하는지 쓴다. 필요한 전문 용어는 처음에 짧게 풀어 설명한다.
- 필수와 권장을 구분한다. “무조건”, “완벽”, “표준 그 자체”처럼 범위를 숨기는 표현을 피한다.
- 금지에는 이유와 허용되는 다음 행동을 붙인다. 안전·권한 핵심은 링크 뒤에 숨기지 않는다.
- 제품 예시는 선택 사항으로 표시한다. 실제 제품 이름으로 공통 적용 범위를 정하지 않는다.

문서의 역할을 나누는 근거는 [Diátaxis](https://diataxis.fr/start-here/)를 참고한다.
문서를 나누는 목적은 파일 수를 늘리는 것이 아니라 독자가 필요한 답을 찾게 하는 것이다.
