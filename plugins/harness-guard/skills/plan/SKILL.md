# plan — 프로젝트 계획 계약

사용자는 목표를 자연어로 설명하면 된다. `/plan`은 선택적인 명시 호출이다.
일반 설계·계획은 사용자가 선택한 방법론 하나를 따른다. 설치된 Superpowers가 선택됐다면 그 산출물을
아래 프로젝트 계약에 맞추며 별도 계획·승인 절차를 다시 시작하지 않는다. 미설치면 native 방식으로
같은 계약을 충족한다. 스킬 설치나 특정 모델을 요구하지 않는다.

## 시작과 승인 범위

- 실제 제품 루트·AGENTS.md·관련 기술 기준·기존 요구/스펙과 직접 소비자를 확인한다. 필요한 API는
  설치된 버전의 원본에서 확인하고 라이브러리 조사를 관계없는 영역으로 넓히지 않는다.
- 기존 계획과 승인된 범위를 재사용한다. 사용자 의도·수용 기준·권한을 바꾸는 미결정만 확인한다.
  이미 승인된 작업을 다시 승인받거나 자명한 수정에 별도 계획 문서를 강제하지 않는다.
- 계획만 요청받았다면 읽기·계획 산출물까지만 수행한다. 앱 코드·브랜치·커밋·PR은 변경하지 않는다.
  계획 권한을 구현·외부 변경 승인으로 확대하거나 plan mode가 없는 도구에서 보호를 가장하지 않는다.

## 프로젝트에 남길 최소 계획

제품의 기존 기록 하나에 아래 내용을 연결한다. 방법론별 계획 파일을 중복 작성하지 않는다.
GitHub 하네스의 새 `feature/<name>` 브랜치가 필요하면 정본을 `docs/specs/<name>.md`에 둔다.
이미 다른 위치에 상세 계획이 있으면 이 파일은 정본 링크와 승인 범위를 담는 짧은 연결 문서로 충분하다.

- 목표·이유, 포함/비목표, 변경하면 안 되는 대상
- 정상·실패·경계에서 관찰할 수 있는 수용 기준(필요하면 AC-ID)
- 영향 파일·호출부·기술 제약, 수용 기준별 검사 명령 또는 판정 방법
- 필요한 만큼의 작은 태스크·의존성·진행 체크리스트와 다음 행동
- 현재 승인 근거와 아직 결정이 필요한 사항

문서 길이·질문 횟수·원자 커밋 개수를 목표로 삼지 않는다. 관련 로드맵·현재 사용 안내는 같은 범위를
가리키도록 맞추고 과거 검증 기록은 당시 후보로 보존한다.

## 개발로 인계

사람 승인 범위를 확인한 뒤 구현을 요청받았으면 기존 계획에서 이어간다. 새 범위의 승인이 필요할 때만
계획과 필요한 선택을 제시한다. `feature/*` 전 스펙 존재 검사는 승인 여부까지 증명하지 않는다.
신규 기능은 `feature-add`, 기존 동작 변경은 `feature-modify`의 프로젝트 계약을 연결한다.
한 기능은 기존 작업 브랜치에서 이어가며, 로컬 제품에는 원격·PR 생성을 강제하지 않는다.
