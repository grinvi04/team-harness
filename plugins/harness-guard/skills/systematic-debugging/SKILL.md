# systematic-debugging — 프로젝트 진단·수정 인계 연결

일반 디버깅은 선택한 Superpowers의 systematic-debugging 또는 native 방법론 하나를 따른다.
먼저 [공통 프로젝트 계약](../ao-coordinate/project-contract.md)을 읽고 재현·원인 판별 결과에 연결한다.
같은 진단을 다시 시작하지 않는다.

## 진단 권한

- **진단 전용 요청은 파일을 수정하지 않는다.** 브랜치·커밋·PR도 만들지 않는다.
- 수정 요청도 근본 원인을 확정하기 전에는 코드를 수정하지 않는다. 진단은 수정 권한을 만들지 않는다.
- 관련 없는 미커밋 변경을 보존하고 수정과 충돌하면 중단·범위를 확인한다. 영향 없는 읽기 조사는 이어갈 수 있다.
- 운영 DB·인프라 변경, 파괴적 시험, 시크릿 출력은 진단 증거로 사용하지 않는다.

## 프로젝트에 남길 진단 증거

- 기대 동작과 실제 동작, 최초 실패 경계
- 현재 후보·입력·환경, 재현 명령·종료 코드와 반복/간헐 조건
- 관찰한 사실과 미확정 추론
- 원인 가설과 판별 실험, 확인/기각 결과
- 원인의 인과 경로·최소 수정 범위 또는 미확정 이유·다음 관측

증상 없이 오류 조사를 요청받았으면 원래 요구와 핵심 사용자 흐름에서 시험 범위를 고른다.
접근 가능한 환경의 정상·실패·경계를 직접 조사하고 업무 의도·접근 권한처럼 조사로 결정할 수 없는 것만 묻는다.
발견한 결함 하나와 원래 목표 달성을 구분하며, 재현 없는 사용자 증상 일치는 미확인이다.
원인을 확정하지 못하면 미확정으로 보고하고 추측으로 수정하지 않는다.

## 수정 인계

원인 확인과 수정 승인이 갖춰지면 feature-modify의 변경·유지 테스트 계약으로 이어간다.
공개 동작에는 자동 회귀 테스트, CI·빌드·설정에는 실행 가능 검사를 사용해 수정 전 RED를 확인한다.
현재 방법론에서 검수한 재현·RED를 중복 작성하지 않는다.
원래 증상·회귀·제품 품질·필수 독립 검증과 문서 현행화는 공통 계약을 따른다.
진단 완료·수정 완료·병합·릴리즈 상태를 구분하며 원인/미확정 사유와 남은 한계를 보고한다.
