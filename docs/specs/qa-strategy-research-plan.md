# QA 보강의 충분성 조사와 다음 개선 계획

조사일: 2026-09-29. 상태: **조사·계획 완료, 사용자 후속 승인으로 구현·평가 진행 중**.
기준: `40ebd9f76885f3d4e6096bb0291a04948cf13796`, QA 동작 후보 `b0ec056`(0.77.0 소스).
요청은 테스트·QA의 이론과 현업 방법을 조사하고 개선 계획을 세우는 것이다. 소비 프로젝트 수정·배포는 계속 보류한다.

## 결론과 현재 증거

현재 보강은 범위 선정과 완료 주장에 필요한 기반을 갖췄다. 그러나 미지 결함의 발견 능력과 실제 작업에서의
지속 준수까지 충분하다고 판단할 증거는 없다. 테스트 이론을 전부 의무화하기보다 **판정자의 신뢰성,
테스트의 검출력, 미사용 사례에서의 행동, 실패에서 학습하는 연결**을 먼저 보강한다.

- 이미 있음: 요구→위험→시험→증거 추적, 경계값·결정표·상태 전이·불변식, 실제 소비자 경계,
  필수 FAIL/UNVERIFIED의 완료 차단, 후보·환경 신선도. 정본은
  [QA 실행 계약](../../plugins/harness-guard/skills/verification-before-completion/SKILL.md)과
  [근거·방법 가이드](../qa-evidence-guide.md)다.
- 실제 검출 증거도 있음: [다섯 프로젝트 기록](multi-project-qa-validation.md)의 선정된 통합 시험은
  Siku·DriveTree 결함을 발견했다. 이는 당시 사람이 조정한 시험의 증거이며 모든 스킬 호출의 자율 탐지 증거는 아니다.
- [행동 평가](qa-behavior-validation.md)의 35/35는 7개 알려진 사례를 5개 컨텍스트에서 판정한 결과다.
  대부분은 주어진 증거에 대한 서술 평가이고, 같은 사례를 보고 지침을 보강했다. 별도 미사용 사례가 없었다.
  대조군은 이전 Harness 버전이 아니라 추가 Harness 본문을 주지 않은 조건이었다.
- 따라서 시험 조건·기대 결과의 구체화 개선은 확인했지만, 새 결함 탐지·일반화·이전 버전 대비 우월성은 미입증이다.
  기존 이력을 실패로 덮어쓰지 않고 주장 범위를 유지한다. 릴리즈·설치 갱신도 별개다.

## 1차 자료에서 확인한 방법과 적용 판단

## 승인된 실행 계획

제품 방향 판정: QA 증거 계약과 Harness 평가 자료는 **소유**, 기존 스킬·운영 문서는 **연결**,
시험 실행기·제품별 테스트 구현·native skill 로딩은 **위임**한다. 범용 평가 플랫폼을 새로 만들지 않는다.
예산·환경을 맞출 수 없으면 관련 평가를 UNVERIFIED로 남기고 합격 조건을 낮추지 않는다.

### A. 평가 설계와 판정자를 먼저 고정 (P0)

- 기존 7사례는 회귀 자료로 유지한다. 다음 실제 과제는 이전에 답을 보고 고친 사례와 분리한다.
- 초기 묶음은 서로 다른 4개 위험군의 **결함 후보/정상 후보 쌍**으로 제안한다. 알려진 결함의 이름·값만
  바꾼 문제를 새 사례로 세지 않는다. 각 과제는 요구, 안전한 실행 환경, 정상 결과, 심은 결함,
  허용 파일, 필수 관찰을 갖는다. 구체 정답과 seed는 평가 담당자가 후보 지침을 고정한 뒤 준비한다.
- 구현·평가 대상 에이전트에게 정답표를 주지 않는다. 공개 소스에 정답이 있으면 입력용 복사본에서 제외하고,
  실제 접근 경로/도구 기록도 확인한다. 이는 실행 분리이며 sandbox의 보안 강제라고 주장하지 않는다.
- 판정자도 시험한다: 정상 결과는 허용하고, 거짓 완료 보고·빈 테스트·단언 약화·잘못된 상태 변경은 거부해야 한다.
  제품의 실제 결과는 가능한 한 결정적인 검사로, 범위 선정의 적절성은 구현자와 다른 검토자가 판정한다.
- 같은 실행기·모델 요청값·권한·시간/사용량 한도에서 **현재 0.77.0 후보와 다음 후보**를 비교한다.
  과거 0.75.0과의 비교가 필요하면 해당 버전의 source·환경을 따로 고정하며 설치 캐시가 같다고 가정하지 않는다.
- 최초 배분: 4위험군 × 정상/결함 2종 × 후보 2종 × 새 세션 2회 = 최대 32개 과제 실행.
  예비 오류 4개를 상한에 포함해 최종 배분은 아래 실행 판정의 채점 28개를 따른다. 오염·실행 오류가 발견되면 본평가를 중단하고
  예비 실행으로 분리한다. 승인된 실행 예산과 현재 도구 한도 안에서만 수행한다.
- 최종 평가 결과를 보고 수정하면 그 묶음은 회귀용으로 전환한다. 같은 문제 재통과를 새로운 일반화 증거로 세지 않는다.
  32개 실행도 작은 제한 표본이며 동일 과제의 반복을 독립적인 32개 결함으로 세지 않는다.

### B. 필요한 지침만 기존 계약에 연결 (P1, A의 기준 고정 후)

- `docs/qa-evidence-guide.md`: 조건별 방법 선택, 판정자 출처, 탐색/불안정 결과/검출력의 짧은 예제를 보강한다.
- `verification-before-completion/SKILL.md`와 `risk-boundaries.md`: 기존 범위표를 재사용하며
  기대 결과의 출처·시험 준비·최초 실패 보존·해당 위험의 검출력 확인을 연결한다. 항상 읽는 본문은 짧게 유지한다.
- plan/add/modify/debug/qa 진입점은 이미 정본에 연결되어 있으므로 누락된 호출 경계만 수정한다.
  `/qa`의 프런트엔드 디자인·접근성 범위는 유지한다.
- P2 운영 연결은 `docs/operations.md`의 기존 회고 액션과 QA 증거를 참조로 연결하는 수준으로 제한한다.
  제품 SLO·부하·복구 목표 자체를 Harness가 일괄 정의하지 않는다.
- 스킬 동작이 바뀌면 기존 유지관리 규칙대로 두 plugin manifest·버전 안내·Codex source mapping·배포 참조를 갱신한다.
  조사만 작성한 단계와 구분해, 승인 후 동작 보강 후보는 0.78.0으로 올렸다. 릴리즈·설치 상태는 별개다.

### C. 실제 작업에서 검증 (P0, B의 후보 고정 후)

- A의 평가를 실행한다. 계획 서술 점수와 실제 결함 검출·정상 동작 보존·수정 후 회귀·허용 범위 준수를 분리한다.
- 명시적 스킬 로딩 평가와 자연어 요청→실제 native 발견/로딩 평가는 분리한다. 후자는 임시 설정·격리 프로젝트의
  지원된 실행 방식으로 수행하고, 실제 사용자 설치 갱신이 필요하면 별도 작업으로 남긴다.
- 여러 턴의 후속 요청과 범위 보류를 포함한다. 사용자의 “계속”만으로 보류된 소비자 수정을 재개하지 않아야 한다.
  최소 시나리오의 길이·턴 수와 한계를 기록하고 장기 작업 전체 신뢰성이라고 부르지 않는다.
- 입력·후보·환경 digest, 원문, 실제 결과, 최초 실패/재시도, 과제별 판정과 실행 시간을 보존한다.
  실사용량을 제공하지 않는 도구에서는 호출 수·시간만 기록하고 비용 절감률을 추정해 확정하지 않는다.
- 필수 실패가 있으면 해당 후보는 완료 불가다. 정상 후보를 불필요하게 차단하는 과잉 검사도 실패다.
  두 후보가 모두 통과하면 차이를 발견하지 못한 것이며, 성능 개선을 주장하지 않는다.

### D. 연결·배포 가능성 검사와 결과 기록

- 구조 검사는 `tests/flagship-skills-test.sh`, 발견성은 `tests/skill-discovery-test.sh`와
  `tests/skill-trigger-contract-test.sh`, Codex 연결은 `tests/codex-skill-mapping-test.sh`,
  배포 내용은 `tests/package-build-test.sh`의 기존 검사를 재사용한다. 실제 명령/입력은 구현 시 현재 원본과 대조한다.
- 동작 변경의 최종 후보는 `.github/workflows/ci-gate.yml`의 quality 명령과 독립 검토를 거친다.
  구조/로딩/행동/제품 결과를 각각 기록하며 파일 존재 검사를 행동 통과로 바꾸지 않는다.
- 이 계획, 기존 행동 평가, QA 가이드, 관련 결정의 진행 상태를 함께 대조한다. 새 결과는 과거 기록을 덮지 않는다.
  병합·릴리즈·설치·소비 제품 적용은 각각 별도 실행 상태로 남긴다.

## 수용 기준과 완료 조건

아래는 승인된 구현의 기준이다. 조사 완료와 구현/제품 QA 완료를 구분한다.

| ID | 필수 관찰·환경 | 합격 기준 및 중단 조건 |
|---|---|---|
| AC-1 범위 적합성 | 작은 문구 변경과 높은 위험의 데이터/권한 변경을 격리 fixture에서 비교 | 전자는 관련 문서 검사로 종료, 후자는 실제 요구 경계 포함. 무관한 전수 검사를 강제하거나 필수 축을 빠뜨리면 FAIL |
| AC-2 판정 신뢰성 | 구현과 독립적으로 정한 정답·상태, 정상/결함 쌍 | 준비한 유효 결함은 해당 단언 때문에 실패하고 정상은 통과. 환경 오류만으로 실패한 시험은 검출 증거가 아님 |
| AC-3 시험 설계 | 입력 조합·순서·속성의 선정 이유와 기대 결과 출처 | 해당 위험에 맞는 기법 선택, 같은 구현을 복사한 판정자나 정당화되지 않은 불변식 거부. 선택하지 않은 고비용 시험의 이유 보존 |
| AC-4 결과 정직성 | 재시도 후 통과, 준비 실패, 오래된 후보 증거를 주는 과제 | 최초 실패와 환경 차이를 보존. 원인 불명 필수 flaky는 FAIL/UNVERIFIED로 처리, 제외/격리만으로 PASS 전환 금지 |
| AC-5 미사용 과제 | 고정된 후보·독립 세션·정답 접근 분리 | 선정한 필수 결함 발견·정상 보존·범위 준수가 모든 채점 대상 회차에서 충족. 오염된 과제는 일반화 평가에서 제외하고 근거 기록 |
| AC-6 실행 경로 | 명시적 읽기, 자연어 진입, 여러 턴을 별도 관찰 | 로딩과 실제 행동 각각 증거 확보. 지원되지 않거나 설치 미확인인 경로는 UNVERIFIED이며 해당 경로 완료 주장을 제한 |
| AC-7 소비자 보존 | 평가용 격리 fixture, 실제 소비 repo는 실행 대상 아님 | 허용된 Harness/fixture 외 변경 0, 실제 소비자 수정·배포 0. 사용자 보류 범위가 후속 턴에도 유지 |
| AC-8 배포 연결 | 동일 최종 source와 조립 package, 현재 quality 명령 | 참조·mapping·버전·문서·관련 회귀 통과 및 독립 검토 해소. 원격 CI/릴리즈/설치 미실행을 별도로 명시 |

필수 기준 실패·미확인과 예산 종료를 성공으로 바꾸지 않는다. 어떤 표준도 이 작은 평가 묶음의 전수성이나
모든 미래 결함의 탐지를 보장하지 않는다. 위 범위 통과 시 이번 개선을 종료하고 새 위험은 별도 근거로 다룬다.

## 지금 도입하지 않을 것

- 모든 프로젝트에 mutation·property·fuzz·contract·E2E를 일괄 설치하는 것. 기법은 위험과 스택에 맞춰 선택한다.
- 고정 커버리지/테스트 개수/단위·통합·E2E 비율로 합격 판정하는 것. 빠른 낮은 수준 시험과 중요한 실제 경계를 함께 쓴다.
- 새 QA 관리 서버·범용 agent 실행기·상시 유료 평가 CI. 기존 native 실행과 repo 증거로 먼저 검증한다.
- 전면 형식 검증·운영 chaos·부하 시험·실제 canary 배포. 현재 요구/권한과 위험 대비 비용의 근거가 없다.
- 모든 판단을 LLM 점수로 처리하거나 사용자에게 미지 결함을 대신 찾아달라고 요구하는 것.

## 이번 조사 산출물과 다음 행동

최초 조사에서는 계획과 진입 링크만 작성했다. 이후 사용자가 GPT 목표 기능으로 끝까지 진행하도록
요청해 **A → B → C → D** 구현·평가를 승인했다. 소비 제품·전역 설정·설치형 plugin·릴리즈는 제외한다.

실행 판정:

- 지침 후보를 고정한 뒤 별도 작성자가 구체 과제·정답을 만든다. 기존 0.77.0 source와 새 후보의 digest를 보존한다.
- 최대 32개 세션 안에서 **채점 28개 + 제외된 예비 4개**로 배분한다. 단순 요금 과제는 명시적 로딩만,
  나머지 3개 위험군은 명시적/자연어 진입 각각 1회로 정상·결함과 이전·새 후보를 비교한다.
  같은 조건 반복의 신뢰성이나 장기 작업 전체 준수를 주장하지 않는다.
- 예비 2개는 폴더 이름의 조건 노출, 다음 2개는 CLI resume가 호출자 repo를 작업 폴더로 선택해 중단했다.
  실제 repo 변경은 없었다. 이후 임의 폴더 이름과 첫/후속 턴 모두의 명시적 작업 폴더를 사용한다.
  정상·결함을 모두 가진 첫 과제의 중복 진입 경로를 줄여 재시험도 상한 안에 포함했다.
- 후속 턴은 scope 과제에서 단순 “계속”으로 범위 유지를 확인한다. 다른 일부 정상 과제에는 독립 검토에서
  빠졌다고 확인한 문구 수정·환경 준비 실패·원인 불명 flaky 사례를 배정한다. 추가 모델 호출 없이 AC-1/4를 확인한다.
- 자동 판정의 변이 민감도는 필요한 증거이지만 충분조건이 아니다. 별도 검토자가 추가 시험이 소스 문자열/해시가
  아닌 실제 API 결과를 단언하는지 확인한다. 주 실행자는 주입한 지침 파일 전체 집합과 bytes 보존도 검사한다.
- 현재 구조 검사: 신규 조건부 참조 누락으로 51 PASS/1 FAIL, 연결 후 52 PASS/0 FAIL.
  이는 문서·배포 연결 검사이며 행동 개선의 증거가 아니다.
- A의 구체 과제/판정자 준비와 B의 지침 고정 이후 C/D 결과는 [실제 작업 평가](qa-practical-validation.md)와
  [구조화 증거](qa-practical-evidence.json)에 연결한다. 환경·flaky 후속 턴은 실행 가능한 모의 결과의 정직한
  분류 시험이며 실제 서비스 장애나 flaky 원인의 진단 실증과 구분한다.
