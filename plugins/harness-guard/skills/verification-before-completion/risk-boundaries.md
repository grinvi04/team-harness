# 위험별 QA 관찰 경계

범위표를 만들 때 변경과 관련된 행만 선택한다. 모든 제품에 DB·브라우저·외부 인증 시험을 강제하는
목록이 아니다. 제품의 요구·채택한 일관성/복구 정책을 기대값으로 쓰며 아래 예시가 새 요구를 만들지 않는다.

| 해당 위험 | 선정할 조건과 판정자 | 충분하지 않은 증거 |
|---|---|---|
| 상태에 따라 편집/이동 금지 | 지출의 부모 FK뿐 아니라 참여자 멤버십 등 간접 관계 FK도 변경 전/후 보호 대상을 각각 확인한다. 잠긴 원본→열린 대상, 열린 원본→잠긴 대상 등 거부 쌍과 정상 허용 쌍을 실제 일반 사용자 API로 시험한다. 거부 응답과 원본·대상 저장값 불변을 함께 본다. | 버튼 숨김, 금액 필드 수정 거부, 변경 후 부모 상태만 검사 |
| 변경 후 목록·검색·캐시 반영 | 변경 전에 같은 키/조건의 목록·검색을 예열한다. 수정/삭제 뒤 동일 소비자의 재조회·새로고침·재진입을 확인하고 채택한 일관성 정책 안에서 DB·API·화면 결과가 맞는지 본다. | DB 변경, 단건 404, 새 검색 조건만 통과 |
| 큐·비동기·중복·실패 복구 | 요청/작업 식별자로 실제 worker의 종결 상태와 영속 결과를 연결한다. 제한 시간 안에 상태를 관찰하며, 멱등 요구가 있으면 중복 요청의 저장/부작용 1건을 단언한다. 실패 payload의 영속 보존·DLQ와 재처리 결과까지 요구된 복구 경계를 확인한다. | 202/queued/재처리 시작, health 응답, 고정 sleep, mock worker 성공 |
| 인증·역할·tenant 경계 | 실제 인증 경로에서 채택한 서명·issuer/audience·만료 계약별 유효 토큰 허용과 잘못된/만료 토큰 거부를 구체화하고, 권한 검사와 분리한다. 해당 쓰기 권한이 있는 정상 주체의 허용 대조군, 다른 tenant 수정/삭제 거부와 저장값 불변을 함께 확인한다. fixture 생성용 service role과 시험 요청 주체를 구분한다. | 대체 claims/관리자 객체, GET 거부만 통과, 애초에 쓰기 권한 없는 사용자의 403 |
| fixture·실행 환경 차이 | 실행 대상이 안전한 격리 환경인지, 계정/역할/tenant·지원 엔진·서버 후보가 맞는지 확인한다. 프로젝트의 환경별 설정을 사용하고 비밀값은 기록하지 않는다. 로컬 고정 계정 통과를 CI의 다른 자격 증거로 재사용하지 않는다. | 개발 PC 상수 계정, 기존 서버 재사용, 다른 후보·설정의 green 로그 |

각 선택 행은 조건·기대값·관찰 경계·필수 여부·후보/환경·증거·판정으로 범위표에 연결한다.
선택한 행의 하위 경계도 개별 판정자로 옮긴다. 예를 들어 인증·fixture 위험이 함께 있으면 다음처럼
작성한다(제품이 채택한 계약에 한정):

- 인증: 정상 토큰 허용; 서명·issuer/audience 오류와 만료 토큰은 각각 거부.
- 권한: 쓰기 권한이 있는 owner는 성공; 다른 tenant의 수정/삭제는 거부되고 저장값 불변.
- fixture: 생성용 service role과 요청 주체 분리; 지원 환경별 설정 자격으로 실행하고 PC 상수 결과와 구분.

관계 이동은 부모 객체와 참여자 멤버십 등 간접 관계를 각각 행으로 써서 양방향 거부·허용 대조군·
저장값 불변을 확인한다. 요약 보고에서도 선정한 하위 경계와 연결된 근거를 추적할 수 있어야 한다.
접근 불가로 실행하지 못한 필수 경계는 UNVERIFIED다. 테스트 수가 많거나 시간이 지났다는 이유로
생략하지 않는다. 새 결함을 발견하면 현재 목표의 완료 판정과 그 제품 결함의 수정 권한을 분리한다.

예를 들어 Harness 기준 보강 중 소비 제품의 부모 이동 결함을 발견했다면, 해당 실패를 잡을 기준과
증거를 Harness에 반영하고 소비 코드 수정은 사용자가 맡긴 범위인지 확인한다. 명시적으로 보류한
제품 수정·배포는 짧은 “계속”만으로 재개하지 않는다. 현재 승인된 Harness 작업은 그대로 완료한다.
