# 프론트엔드 디자인 표준 — 디자인 시스템·컴포넌트·함정

[표준 적용 기준](standards-scope.md)을 따른다. 사용자 과제와 기존 디자인을 우선한다.
반응형·접근성·실제 상태 표시는 공통 기준이다. 다크모드·앱 셸·차트는 필요한 제품에서 선택한다.
특정 SaaS 화면이나 라이브러리를 모든 프로젝트에 강제하지 않는다.

---

## 0. 전제 원칙 — 프레임워크·라이브러리는 **현재 공식 문서로 확인**

프레임워크/UI 라이브러리는 자주 바뀐다. **학습 데이터/관성으로 API를 가정하지 말고 그 시점의 공식 문서로 확인한다.**
(`stack-guide.md`: "최신 안정 버전은 킥오프 시 공식 릴리즈로 재확인". 프로젝트 룰 예: "This is NOT the Next.js you know — `node_modules`의 해당 가이드를 읽고 작성, deprecation 준수".)

- 버전·시그니처·SSR/RSC 경계·deprecation은 **설치된 버전의 공식 문서**가 1차 출처.
- 아래 §5~6의 구체 코드는 **특정 시점·스택의 사례**다. 그대로 복붙하지 말고, **같은 "부류"의 함정을 너의 스택 공식 문서로 확인**하라(요지는 패턴이지 특정 API가 아니다).

## 1. 디자인 토큰 (프레임워크 무관, 첫 작업)

토큰 기반 디자인을 채택하면 색·간격을 의미 있는 이름으로 정의한다. 지원하는 테마만 채운다.
CSS 변수, Tailwind의 지원 버전 설정, CSS-in-JS 테마 등 기존 기술에 맞는 방식을 선택한다.

토큰 기반 디자인을 채택했다면 필요한 의미별 토큰을 정의한다. 아래는 예시다:
- 표면/텍스트: `background` `foreground` `card` `popover` `muted` `muted-foreground` `border` `input` `ring`
- 브랜드: `primary`(+`-foreground`) `accent`(+`-foreground`)
- **상태**: `destructive` **`success` `warning`**(+`-foreground`) — 배지·경고·증감에 필수
- **차트 팔레트**: `chart-1`~`chart-5`(인디고·틸·앰버·로즈·바이올렛 같은 **카테고리 구분색**). ⚠️ 회색 단색이면 차트가 흑백이 된다.
- (해당 시) 사이드바 토큰군

규칙:
- 토큰을 채택한 화면에서는 의미 토큰을 사용한다. 색 값은 토큰 정의에 둔다.
  브랜드 이미지·데이터 시각화처럼 직접 색이 필요한 예외는 이유와 테마 대비를 확인한다.
- 차트 데이터색은 브랜드색으로 뭉치지 말고 `chart-1~5`로 카테고리 구분.
- 다크모드를 지원하면 다크 토큰도 정의하고 실제 화면에서 확인한다.
- 금액·수치는 등폭(tabular) 정렬.

## 2. 앱 셸

앱 셸이 필요한 제품의 선택 예시다. 검색·테마·프로필은 실제 기능이 있을 때만 둔다.

- **사이드바**: 토큰 기반, 브랜드 마크, 섹션 라벨, 접이식 그룹, 절제된 활성 인디케이터.
- **헤더**: 검색(커맨드 팔레트)·테마 토글·프로필.
- **반응형**: 사이드바 네비를 **한 컴포넌트로 분리**해 데스크톱 고정 패널과 모바일 드로어가 재사용.
- 배경도 토큰. 하드코딩 배경색 금지.

## 3. 공통 컴포넌트 (화면 만들기 전에 프리미티브부터)

반복되는 화면 요소만 공통화한다. 모든 제품에 아래 컴포넌트를 미리 만들 필요는 없다.

| 컴포넌트 | 역할 |
|---|---|
| PageHeader | 제목·설명·우측 액션 — 화면 상단 통일 |
| StatCard | KPI(라벨·값·아이콘 칩·추세·옵션 링크) |
| EmptyState / ErrorState | 빈/오류 상태 일관 |
| ChartCard | 차트/콘텐츠 카드(드릴다운 링크) |
| **DataTable** | 정렬·행선택·일괄액션·스켈레톤·빈상태. 반복 요구가 있을 때 공통화 |
| **FormField** | 라벨·필수표시·**인라인 에러/힌트**(toast 검증 대체) |

- 복잡한 목록은 필요한 정렬·선택·접근성을 지원하는 테이블을 선택한다. 단순 목록에 과한 구조를 강제하지 않는다.
- 폼 검증은 **필드 인라인**(toast만 쓰지 말 것).

## 4. 차트

차트가 사용자의 판단을 돕는 경우에만 적용한다.

- 색은 **차트 토큰 변수**로 — 라이트/다크 자동 적응.
- 비교·추세·분포 등 사용자가 읽을 과제에 맞춰 차트 유형을 선택한다.
  시계열의 라벨과 값은 시간 필드로 연결한다. 배열 위치만 연결하면 빠진 날짜에서 어긋날 수 있다.
- 테마 툴팁(팝오버 토큰), 축·그리드도 토큰색.
- 서버 렌더 경계를 넘는 일반 포맷 함수는 클라이언트에 둔다. 직렬화 가능한 설정 값으로 전달할 수 있다.
  지원되는 Server Action은 별도 경계다. [공식 전달 조건](https://nextjs.org/docs/app/getting-started/mutating-data#passing-actions-as-props)을 확인한다.

## 5. 스택별 UI 라이브러리 함정

사용법·prop·타입은 설치한 라이브러리의 공식 자료를 따른다.
같은 이름의 컴포넌트라도 trigger 합성·체크박스 상태·툴팁 payload가 다를 수 있다.
타입을 느슨하게 만들어 오류를 숨기지 않는다. 실제 타입과 이벤트 경계를 확인한다.
자세한 확인 경로는 [프론트엔드 문제 해결](stack-troubleshooting-frontend.md)에 둔다.

## 6. 프레임워크 상태/렌더 함정

파생 상태·effect·props 변경·선택 상태는 해당 프레임워크의 공식 동작을 따른다.
일반 함수와 Server Action을 구분한다. 데이터 참조·row key·재마운트 조건은 라이브러리별로 확인한다.
특정 렌더 패턴을 모든 컴포넌트의 해결책으로 적용하지 않는다.
[스택별 진단 경로](stack-troubleshooting-frontend.md)를 현재 버전과 대조한다.

## 7. 접근성·정직성 (프레임워크 무관)

- 정렬 헤더 `aria-sort`, 토글 `aria-label`, 입력 오류 `aria-invalid`. 색 대비 확보.
- **동작 안 하는 컨트롤을 그리지 말 것** — 클릭해도 무반응인 검색창, 안 읽은 점이 켜진 가짜 알림 벨은 거짓 신호다. 실제 기능을 붙이거나 제거. (값이 늘 비는 **dead 데이터 컬럼**, 예: 헤더만 있고 채워지지 않는 '예약/가용' 열도 같은 거짓 신호 — 채우거나 제거.)
- 다중통화는 제품의 환산·표시 계약을 따른다. 환산 합계를 제공하는 제품은 기준통화 합계와 통화별 내역을 함께 표시할 수 있다.
  환산하지 않는 제품은 통화별로 표시한다. 서로 다른 통화를 그대로 더하지 않고 금액·통화가 잘리지 않게 한다.

## 8. 검증 (PR 전, 프레임워크 무관)

- [QA 범위·완료 기준](ai-collaboration.md#qa-범위와-완료-기준)에 따라 제품이 지원하는 화면·상태와
  변경 위험을 먼저 고른다. 각 사례의 기대 결과를 시험 전에 정하고 비지원·비적용 조합은 이유를 남긴다.
- `type-check`(있으면)·lint·build 통과.
- 제품이 지원하고 변경 영향이 있는 **라이트·다크·모바일(+드로어) 대표 조합을 실제 브라우저 자동화로 스크린샷**
  캡처해 눈으로 확인(차트가 다크에서 보이는지·금액이 잘리지 않는지).
- 데이터가 있는 화면이 검사 대상인데 데이터 0 환경이면 **격리된 테스트 데이터**로 차트·KPI를 실제로 본다(빈 화면으론 품질 판단 불가).

### 정적 검사와 실제 화면 검사 연결

- **정적 검사:** 사용하는 파일 형식에 맞게 코드·접근성 lint와 색상 토큰 검사를 연결한다.
  제공하는 `templates/frontend/check-design-tokens.mjs`는 `src`의 JS/TS/JSX/TSX에서 특정 Tailwind
  색상 클래스를 찾는 검사다. Vue 파일·CSS·동적 스타일·모든 직접 색상을 검사한다고 해석하지 않는다.
  Vue/순수 CSS 제품은 Stylelint 등으로 CSS와 Vue `<style>`을 검사하고, 색상 정의를 허용할 토큰 원본을
  명시한다. 직접 색상·미정의 변수의 거부, 정상 토큰·유효한 라벨 연결의 허용을 함께 확인한다.
  Vue template의 접근성 lint는 CSS 검사와 별도로 연결한다.
- **실제 브라우저:** Playwright 같은 도구로 정상·빈 목록·편집·실패/재시도 중 요구·변경에 관련된 화면을 확인한다.
  위에서 선정한 대표 조합에서 axe 같은 접근성 검사를 실행하고, 조작에 영향이 있으면 키보드 초점 이동도
  별도로 단언한다. 저장·취소뿐 아니라 검색/필터 때문에 원래 버튼이 사라지는 경우의 초점 복귀를 포함한다.
- **데이터·화면 경계:** 긴 이름·연속 문자열·최대 허용 입력과 빈 값, 레이아웃 전환 폭의 전후처럼
  변경에 노출된 경계를 고른다. 필수 정보·컨트롤이 가려지거나 겹치지 않고 조작 가능하며, 제품의
  줄바꿈·생략 정책과 일치하는지 실제 화면과 치수·초점 단언으로 확인한다. 모든 폭·브라우저 조합의
  전수 검사는 강제하지 않는다. 브라우저별 차이는 지원 환경에서 재현하고 필요하면 네이티브 최소 사례로
  제품 결함과 실행 환경 차이를 구별한다. 원인을 확인하지 않은 실패를 기대값 완화로 해결하지 않는다.
- **판정과 보고:** 접근성 보고서의 `violations`와 `incomplete`를 함께 보존한다. 위반 0건이어도
  자동 판정 불가, 스크린리더·확대·동적 스타일 등 실행하지 않은 범위는 통과로 바꾸지 않는다.
  직접 확인한 화면·상태·후보 커밋과 남은 검토를 제품 기록에 남기며, 전체 WCAG 준수로 확대하지 않는다.

검사기의 설치·CI 연결과 정상/거부 예제 확인은 [온보딩](onboarding.md#스택별-검사를-연결하는-방법)을 따른다.
새 검사 엔진이나 공용 앱 테스트를 Harness에 복제하지 않고 제품의 기존 검사 명령에 연결한다.

## 9. 적용

- 신규 프로젝트는 사용자 과제와 기존 제약을 먼저 확인한다. 필요한 구성만 선택한다.
- 토큰·앱 셸·공통 컴포넌트를 채택했다면 작은 대표 화면에서 확인한 뒤 필요한 곳으로 확장한다.
- 기존 프로젝트의 구조를 보존한다. 다크모드를 지원하지 않으면 다크 정상화를 요구하지 않는다.
- 프레임워크별 사용법은 해당 버전의 공식 자료로 확인한다. 공통 접근성·상태 표시는 유지한다.

## 10. 작업 프로세스

1. 제품의 톤·정보 밀도·지원 환경을 정하고 중요한 사용자 과제 하나를 먼저 확인한다.
2. 채택한 디자인 구조 안에서 필요한 요소만 구현한다. 재사용은 실제 반복이 생겼을 때 검토한다.
3. 라이브러리 API와 타입을 작성 전에 읽는다. 이름이 같아도 사용 조건은 다를 수 있다.
4. 정상·빈 상태·긴 입력·실패 상태를 합성 데이터로 확인한다. 실제 고객 데이터를 자동 사용하지 않는다.
5. 프로젝트가 요구하는 독립 리뷰에서 가짜 컨트롤·접근성 누락·상태 누수를 확인한다.
6. 변경에 영향을 받는 기존 UI 검사를 새 계약에 맞춘다. 오류를 숨기거나 기대값을 약화하지 않는다.
7. 변경은 검토 가능한 단위로 나눈다. 필요한 후속 적용과 미적용 범위를 제품 기록에 남긴다.

## 11. 한국어 UI/UX (한국 서비스·한국어 화면 전용)

한국어 용어·문장·표시 형식은 [한국어 UX 안내](korean-ux.md)를 따른다.
통화·날짜 형식·말투는 제품이 정한 계약과 대조한다. 한국어 화면이라고 원화를 강제하지 않는다.
`templates/rules/korean-ux.md`와 `/qa`의 해당 안내도 같은 조건을 사용한다.
다국어 제품은 지원하는 언어별로 확인한다. 언어와 무관한 접근성·권한 검사는 유지한다.
