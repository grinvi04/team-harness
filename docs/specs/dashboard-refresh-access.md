실행 원문·화면의 `.runtime/` 경로는 저장소 루트 기준의 로컬 보존 자료이며 배포 파일에는 포함하지 않는다.
현재 소스: **실제 사건 UI1.3.0**. 발행·설치와 자동 연결의 [현재 종료 판정](#확인-범위-종료--2026-11-09)을 확인한다. 구현·실제 실행·미확인 범위를 구분한다.
아래 날짜별 요구·1.2.1·시안·검증·전달 절은 당시 후보와 결과의 스냅샷이다. 현재 종료 판정이 과거 실패나 미확인을 소급해 바꾸지는 않는다.

## 설계·작업 순서

1. 기존 fragment→메모리 방식의 새로고침 실패를 재현한다.
2. 같은 origin의 탭 세션 저장소에 토큰 하나를 보관한다. fragment가 있으면 이전 토큰을 대체하며
   잘못된 명시 fragment에서 과거 자격으로 돌아가지 않는다. URL에서는 즉시 제거한다.
3. 새로고침에도 서버 context 인증과 응답 검증을 새로 수행한다. 서버 token·Host/Origin·GET-only·
   loopback·CSP·응답 제한은 유지한다. 401/403 또는 context 인증 실패 시 해당 자격의 삭제를 시도한다.
   늦은 이전 응답은 새 토큰을 지우지 않는다. 저장소 접근 불가 시 첫 CLI 인증만 허용하고 복원하지 않는다.
4. 프론트 정본·배포 생성물·문서·두 manifest/README를 미발행1.2.1 후보로 맞춘다.
5. 단위·서버 경계·실제 브라우저 새로고침과 독립 보안 검토로 현재 후보를 대조한다.

쿠키는 localhost의 서로 다른 포트를 함께 다루므로 추가 서버 세션을 만들지 않는다.
URL에 토큰을 남기거나 localStorage로 영구 보관하지 않는다. query 캐시는 계속 메모리에만 둔다.
sessionStorage는 브라우저의 탭 복원·opener 복사에 포함될 수 있다. 디스크 비저장이나
완전한 탭 간 격리로 홍보하지 않는다. 복원한 토큰도 현재 서버의 인증을 통과해야 한다.
동일 origin의 악성 script까지 막는 별도 인증 방식은 아니며 기존 CSP를 유지한다.
저장소 삭제 자체가 거부되면 삭제를 보장하지 않는다. 남은 값도 서버 재인증을 우회하지 못한다.
snapshot 인증 실패 때 기존 화면은 마지막 관측값·현재 미확인으로 남으며 즉시 데이터 삭제를 뜻하지 않는다.
