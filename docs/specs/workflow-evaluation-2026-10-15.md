## 목적·현재 구조·권한

혼자·작은 팀의 개발자가 현재 Harness로 시작·업무 수행·인계할 때 목표와 검사를 유지하는지 평가한다.
기능 개발만이 아니라 설계·원인 진단·유지보수·검증·리뷰·인계를 하나의 흐름에서 확인한다.
근거는 [제품 방향](../product-direction.md), [사용 흐름](../development-coordination.md),
[로컬 검사](../local-development.md), [native 실행 계약](../../plugins/harness-guard/codex/native-runtime.md)이다.
재사용 구성·검사·증거는 소유, 플랫폼 실행은 위임, 제품의 업무 규칙은 제품에 남긴다.

현재 로컬 생성기는 단독6스택을 선택해 `scripts/check-harness.sh` 하나를 연결한다. 앱 생성기가 아니다.
Spring Boot+Vue 로컬 조합·기본 선택·backend/frontend 옵션은 없다. GitHub 셋업·CI 조합은 유지된다.
현재 스택별 필수·선택 검사는 `templates/stacks.json`과 안내 원문에서 기대값을 도출한다.
Spring/Vue 보존·신규 npm4앱 실행·회귀20개·품질74단계는 기존 후보의 증거로 대조할 수 있다.
이 계획을 썼다는 이유로 코드·검사·버전·기존 보호를 변경하거나 초기 설정을 다시 적용하지 않는다.

10월14일은 계획만 작성했다. 10월15일 세 흐름 실행·검증을 승인받아 로컬 격리 시험과 관련 기록을 진행한다.
필요한 Harness 결함 수정은 기존 승인 범위에 한정하며 소비 저장소·전역 설정·원격 보호는 바꾸지 않는다.
PR·병합·태그·설치·운영·DB/Auth/Storage·실제 회사/사람 인수는 이 계획에 포함하지 않는다.
Claude 실호스트는 기존 미확인 보류다. 해당 검사를 이 계획의 완료 조건으로 다시 추가하지 않는다.

## 새 비교 조건

대조군은 현재 native 플랫폼+동일한 제품 요구·지침·검사다. 후보는 여기에 현재 Harness 계약을 연결한다.
두 조건 모두 같은 시작 소스·검사 기대값·요청 단계·도구·모델·effort·권한·승인 범위·격리 설정을 사용한다.
공통 전역 지침이나 이미 적용된 hook은 비교를 위해 끄지 않는다. 양쪽 실제 유입과 불변을 기록한다.
대조군에도 Harness가 유입되면 순수 미사용군이라 부르지 않고 명시 연결의 추가 효과만 평가한다.
검사·보호·no-log 조건을 한쪽만 빼서 후보의 이점을 만들지 않는다. 차이는 제공한 Harness 문맥으로 제한한다.
현재 원본의 관련 계약·실제 loader 경로·버전·digest를 실행 전에 고정한다. 구버전 설치와 신버전 소스를 섞지 않는다.
직접 공급한 계약의 적용과 자동 skill 발견·hook 실제 실행은 별도 주장으로 기록한다.
계약 적용은 읽기/실행 원문과 결과로 확인하며 파일 존재·프롬프트 첨부만으로 자동 적용을 통과시키지 않는다.
별도 문맥·폐기 작업공간을 사용하고 최소 설정 전후 원문·실제 실행 헤더·원본 지침 digest를 보존한다.
인증값은 기록하지 않는다. 임시 인증 사본을 사용하면 종료 시 제거 확인만 남긴다.

## 평가할 세 연속 흐름

아래 예시는 합성 제품이다. 답이나 이전 평가 결과를 노출하지 않은 새 요구·검사로 실행 전에 확정한다.
기대값은 업무 규칙·유지 계약에서 정하고 구현자가 만든 출력으로 바꾸지 않는다.

| A 처음 연결 | 준비된 Node API·React/Vite 앱의 기존 지침·작업을 확인 → 별도 앱 선택 → preview → 승인된 apply → 검사 | 첫 확인은 수정0; 조합 자동 적용0; preview 쓰기/네트워크0; apply checker1개; 기존 파일·필수 제품 검사 보존 | 적용 전후 파일 digest·명령 원문·생성 내용; 정상과 누락/중복 lock·기존 목적 파일 거부 |

B는 메모리 기반 합성 제품의 규칙이며 운영·실DB 정합성 시험으로 보고하지 않는다.
C는 native 소유자의 PID·nonce·시각·진행 관측을 사용한다. 직접 OS 조회 권한이나 새 상태 서버를 요구하지 않는다.
작은 팀은 독립 문맥·소유 범위·통합 검사로 대표한다. AI 역할 실행을 실제 동료/회사 인수로 부르지 않는다.
6스택의 공통 CLI·보존·거부 경계는 기존 계약 회귀를 대조한다. A의 두 스택 실행을6스택 실제 실행으로 확대하지 않는다.

## 판정표: 정확성과 효용을 분리

| 축 | 기준·자료 | 판정 |
|---|---|---|
| 요청·범위 | 각 단계의 목표·유지 조건·승인과 실제 파일/명령이 일치 | 필수 PASS/FAIL/UNVERIFIED |
| 기능·검사 | 독립 기대값에 정상은 통과·알려진 결함은 해당 이유로 실패; 필수 검사 대체/약화0 | 필수 PASS/FAIL/UNVERIFIED |
| 재개·보고 | 현재 원문·후보·writer 관측·실패/미실행이 인계와 일치 | 필수 PASS/FAIL/UNVERIFIED |
| 문서·설정 | 관련 안내의 버전·명령·완료/미완료와 실제 후보가 일치 | 필수 PASS/FAIL/UNVERIFIED |
| 추가 효과 | 설정 누락·범위 이탈·오판·중복 단계·수동 정정 건수와 구체 사례를 조건별 기록 | 개선 관측/차이 없음/악화/미확인 |
| 비용 | 실제 시간·명령 수·토큰·공급 문맥 bytes를 수집; 명령 출력 bytes와 읽기량 구분 | 관측값; 생산성·요금 절감으로 환산하지 않음 |

결과 판정은 배우 exit0·PASS 문구가 아니라 독립 검토자의 요구·원문·파일·명령 대조다.
문맥 비용이 커지거나 양쪽 모두 통과하면 그대로 기록한다. 이득 없는 resolver/cache/요약 계층은 추가하지 않는다.
표본에서 차이가 나도 인과적 개선·통계적 유의성·사람 생산성을 주장하지 않는다.
추가 효과 미입증은 그 이유만으로 검증된 기능을 실패로 바꾸지 않지만 효과 주장·새 계층 채택 근거가 될 수 없다.
모든 답변 사실·모든 환경·장기 압축·모든 모델·파일시스템 전체 불변은 이 표본의 보장 대상이 아니다.

## 작업 순서·종료 조건

1. 현재 후보·직접 소비자·제품 요구를 고정하고 새3흐름의 단계별 입력·독립 기대값·금지 행동을 확정한다.
2. 기존 원문을 새 기준에 대조해 재사용/미충족/비적용을 구분한다. 범위·후보가 다른 PASS는 옮기지 않는다.
3. 실행 재개 시3흐름×2조건=6세션을 우선 실행한다. 단계별 요청/응답·실제 명령·설정·파일 관측을 보존한다.
4. 필수 독립 검토가 정상·거부·누락과 답변/실제 결과 불일치를 확인한다. 실패는 후보·원인·영향 기준에 연결한다.
5. 구현 수정이 필요하면 승인 범위의 Harness 결함만 고치고 영향 검사만 재실행한다. 소비 제품 결함은 따로 보고한다.
6. 현재 판정·변경·한계를 진행 문서에 연결한다. 커밋·artifact 확인은 전달 요청 범위에 맞춰 별도 수행한다.

실행 수는 목표가 아니다. 최초6세션 뒤 동일 실패의 무변경 반복은 금지하며 새 증거가 있는 영향 재시험만 허용한다.
추가 계획은 최대6세션의 영향 확인으로 한정한다. 필수 기준을 못 채우면 실패/미확인과 필요한 조건을 보고한다.
이전30회는 과거 기록이며 이 계획의 실행 횟수에 섞지 않는다. 새 세션 수·시간·토큰은 별도 계수한다.
필수 기준 전체 PASS·미해결 차단0·관련 품질·문서 일치·독립 검토가 확인되면 해당 로컬 평가를 종료한다.
실행 원문은 로컬 `.runtime/current-evaluation-20261015/`에 보존한다. 독립 검토2회와 최종 기록을 대조했다.
최초 평가기는 `.npm-cache` 전체를 제외해 B·C의 npm 자동 로그 생성과 대조군 B의 기존 로그 삭제를 놓쳤다.
기능 PASS를 범위 PASS로 확대하지 않는다. 재시험은 B·C 캐시 파일도 단계별로 관측하고 controller 쓰기를 구분한다.
수정 계약은 자동 생성·삭제도 쓰기로 다루며 no-log 옵션의 기존 파일 삭제 부작용과 실패 exit 보존을 확인한다.
Unix npm11.6.2의 별도 no-file sink는 정상 exit0·실패 exit7·기존 로그 불변을 폐기 fixture에서 확인했다.
영향 재시험은 B 진단 변경0·승인 후3파일·루트7 PASS, C 허용3파일·summary4 PASS·전체exit1 보존을 확인했다.
C의 owner는 시험 종료 후 writer를 정상 종료했다(exit -15). 제품 library 실패는 해결되지 않았다.
추가 배우 재실행이 필요한 잔여 필수 기준 실패는 없다는 독립 판정이며, 생산성·발행·설치 완료는 아니다.
