# 시험 설계와 판정자 선택

관련 쟁점만 기존 요구·범위표에 연결한다. 모든 기법을 설치·실행하는 체크리스트가 아니다.
제품의 도구와 수용 기준을 사용하고, 무관한 변경에 새 서류나 별도 승인 단계를 요구하지 않는다.

| 쟁점 | 선택과 충분성 판단 |
|---|---|
| 무엇이 정답인지 모호함 | 구현 전에 업무 규칙·수용 예제로 기대값을 확인한다. 테스트와 구현이 같은 계산을 복사하거나 현재 출력으로 snapshot을 갱신하면 독립 증거가 아니다. 모호함이 결과를 바꾸면 필요한 선택만 묻고 나머지 검사는 진행한다. |
| 많은 입력·환경 조합 | 동등 분할·경계값·결정표를 먼저 고른다. 조합이 커지면 t-way 표본과 제외 제약을 기록한다. pairwise만으로 중요한 3개 이상 조건이나 행동 순서가 덮였다고 하지 않는다. |
| 순서·반복에 따라 달라지는 상태 | 모델/속성 기반 시험으로 허용·거부 전이와 각 단계의 불변식을 확인한다. 생성 seed·최소 실패 순서를 보존한다. 모델이 구현을 복제하지 않게 하고, 정확한 기대값이 어렵다면 업무상 성립하는 입력 변환 전후 관계를 먼저 정당화한다. |
| 독립 배포되는 API·이벤트 소비자 | 실제 소비자의 기대와 제공자 응답을 양쪽에서 검증한다. 계약 시험은 저장·인증·복구 요구의 실제 통합 시험을 대체하지 않는다. 단일 앱에 별도 계약 서버 설치를 강제하지 않는다. |
| green 시험의 검출력 의심 | 중요한 단언을 알려진 결함 또는 안전한 임시 변이(거부 조건 반전·경계 오류 등)에 대조한다. 정상 후보는 PASS, 결함 후보는 해당 요구 때문에 FAIL이어야 한다. 빈 테스트·단언 삭제도 성공하는지 확인한다. 실행 불가/잘못된 변이/실제 동작이 같은 변이는 검출 성공으로 세지 않는다. 보편적인 mutation 점수는 요구하지 않는다. |
| 원인 미상·새 사용자 흐름 | 탐색할 목적/가설, 지원 환경, 제한 시간, 관찰과 종료 조건을 짧게 정한다. 발견한 위험에 따라 다음 시험을 바꾸고 재현 가능한 결함은 회귀 검사로 연결한다. 시간 종료·반례 미발견은 제품 전체 PASS가 아니다. |
| 첫 실패 뒤 재시도 성공 | 첫 실패와 이후 실행의 후보·환경·seed·순서를 보존한다. 시험 격리 문제, 의존 서비스 준비 실패, 실제 제품 경합을 구분한다. 단순 재실행 green이나 quarantine은 원인 해소가 아니다. 필수 결과가 불안정하면 FAIL/UNVERIFIED로 남기고 필요한 수정·담당·재검증 조건을 기록한다. |
| 성능·접근성·복구·보안 품질 | 제품이 채택한 지원 환경·업무 부하·지표·임계값·복구 목표/위협 경계를 연결한다. 자동 도구가 관찰하지 못한 사용자 조작이나 실제 복구 결과는 별도 미확인이다. 기준 부재를 임의 숫자로 통과시키지 않는다. |

검출력 확인은 수정 권한이 있는 격리 사본에서만 한다. 직접 검증 요청처럼 수정 권한이 없으면 기존
RED/GREEN 증거를 대조하거나 누락으로 보고하며, 소비 프로젝트·운영·잠긴 시험을 임의로 바꾸지 않는다.
새 검증기는 정상/결함 대조로 검사하고, 스킬 평가는 개발에 사용한 사례와 미사용 과제를 구분한다.
에이전트의 설명과 최종 파일·저장 상태가 다르면 실제 결과로 판정한다. 정답이나 이전 평가가 노출된
사례는 회귀 자료로 보존할 수 있지만 미사용 평가로 보고하지 않는다.
