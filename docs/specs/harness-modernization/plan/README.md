# Team Harness·전역 설정·소비 문서 개선 계획

작성: 2026-10-09 KST. 승인된 실행은 [현재 스펙](../../harness-modernization.md)과 [전달 기록](../execution-delivery.json)을 따른다.
이 진입점의 착수 원본·미확인 목록은 당시 기록으로 보존하며 최신 결과와 구분한다.
계획 방법론은 Superpowers writing-plans 하나이며 Harness plan·QA 계약을 연결한다.
구현자는 승인된 계획에서 이어간다. 별도 계획·승인 workflow를 반복하지 않는다.

## 목표와 변경 이유

확인된 안전 검사·증거 판정 결함을 고치고, 최신 모델의 공식 지원과 과제 품질에 맞게 설정을 재선정한다.
전역 지침·Team Harness·네 소비 프로젝트의 모든 소유 MD를 199줄 이하로 구성한다.
문서만 짧게 만드는 대신 실제 읽기 경로·직접 소비자·현재 구현과의 일치를 함께 검증한다.
근거: [검토보고서](../review/REVIEW.md), [범위와 원래 완료 기준](../review/04-coverage-design.md).
원래 지시와 이행 상태는 [사용자 지시 대조](../review/09-user-instruction-audit.md)에서 확인한다. 발견 57개의 연결만으로 지시 충족을 판정하지 않는다.

## 고정할 경계

- 2026-10-09 사용자가 모든 승인 작업 종료까지 실행하도록 승인했다. 아래 단계와 수용 기준을 적용한다.
- Harness: 공통 정책 검사·후보 증거·GitHub delivery 계약은 소유한다.
- 모델 선택·skill 로딩·hook lifecycle·권한 엔진은 native 기능에 위임하고 필요한 결과만 연결한다.
- 소비 repo: 지침·문서와 그 직접 독자만 정렬한다. 관련 없는 앱 기능·테넌트 구현을 새로 만들지 않는다.
- 배포·운영 DB·유료 환경·결제·새 계정 연결은 제외한다. 기존 배포 보류를 재개하지 않는다.
- 외부 plugin 원본·cache·backup·인증정보·사용자 취향은 편집하지 않는다.
- 모델·effort는 기존 저장값을 기준으로 유지하지 않는다. Sol 6.1 기본·중요 판단 Astra라는 합의에서 평가한다.
- 원래 QA 기준·독립 검증·서버 gate를 낮추거나 과거 PASS를 새 후보에 옮기지 않는다.

## 세부 작업의 책임

전체 대화의 지시와 합의에서 필요한 조사·분해·검사·판정·기록을 agent가 정한다. 사용자가 항목을 하나씩 지정할 필요는 없다.
새 권한·파괴적 변경·추가 비용의 선택만 확인한다. 같은 방향의 세부 경로·파일명·시험 방법은 근거를 정해 진행한다.
안전하게 가능한 검토 시험은 직접 실행하며, 실제 변경 후보가 필요한 검증은 해당 단계의 필수 gate로 둔다.
사용자에게 QA를 수행하게 하거나 미확인 항목을 단순히 돌려주지 않는다. 합의한 설계를 구현하며 배포·운영·결제 제외 경계는 유지한다.

## 단계 0 — 착수 시점 원본과 지원 조건 (당시 기록)

- [현재 버전·원본 증거](../planning-source-state.json): Codex CLI 0.161.0, Claude CLI 2.1.267.
- Harness HEAD `980fe87b4429e601e7f95155063eb2c28906fbaf`; 기존 `.gitignore` 변경은 보존한다.
- Codex config는 감사 초기에 비해 변경됐다. 현재 digest를 기준으로 삼고 작성자를 추측하지 않는다.
- 실제 구현 직전에 해당 원본·설정·직접 호출부만 재확인하고 기존 사용자 변경과 분리한다.
- 최신 Claude 모델 시험은 실제 사용할 앱/CLI의 지원 버전·provider·모델 가용성을 확인한 뒤 시작한다.
- 기본 실행 위치는 로컬이다. 전역 설정·로컬 hook은 로컬에서, 고정 repo 후보는 CI에서도 확인한다.
- 적합한 작업용 checkout을 재사용하거나 분리한다. 현재 무관한 브랜치에 개선 작업을 섞지 않는다.
- 긴 독립 실행 때 project-map 계약을 적용하되, 조사만 승인된 동안 지도 원본을 쓰지 않는다.
- 승인 후 계획의 정본을 `docs/specs/harness-modernization.md`에 연결한다. 임시 계획을 병렬 상태 등록부로 운영하지 않는다.

## QA·종료 조건

- 수정 전 재현 → 수정 후보의 기대 결과 → 정상 대조군 → 직접 소비자 순서로 증거를 남긴다.
- 필수 항목은 후보 SHA/미커밋 diff·실행 파일·작업 경로·환경·명령·종료값·관찰 결과를 연결한다.
- 환경 실패·접근 불가·미실행은 UNVERIFIED다. 실제 비적용만 SKIP이고 실패한 필수를 제외로 바꾸지 않는다.
- 모델 품질 비교와 설정 구문/실제 모델 확인은 별개다. 사용량 미제공을 비용 0으로 쓰지 않는다.
- 완료는 승인 범위의 필수 PASS, 미해결 차단 결함 0, 문서 현행화, 필요한 독립 검토가 함께 충족될 때다.
- source 구현·로컬 적용·CI·병합·릴리즈·설치·배포 상태를 구분한다. 제외한 배포는 완료 조건에 넣지 않는다.

## 착수 당시 계획 검토 결과

확인한 실패 유형 다섯 가지를 각 담당 단계에 배치했다: 입력 표현 누락(1), 후보 교체(1·2), 실패 은폐(2),
설정과 실제 실행의 차이(3), 문서 분할로 reader/역사가 깨짐(4). 최종 인수에서 다시 결합 경계를 확인한다.
같은 계획을 다른 workflow로 복제하지 않으며 새 기능·실험은 요구 품질 또는 확인된 결함과 연결될 때만 추가한다.

[착수 준비 추가 확인](../review/11-implementation-readiness.md)에서 적용/복구·혼합 버전의 검증 조건을 구체화했다.
1단계의 범위·반례·판정자는 착수 가능한 수준이다. 수정 승인과 기준 원본 확인 후 시작하며,
고위험 단계 완료와 실제 전역 적용은 위 미확인·지원 조합 검증을 먼저 충족해야 한다. 새 전면 감사는 요구하지 않는다.
