# feature-add — 신규 기능의 프로젝트 계약

사용자는 만들 기능을 자연어로 요청한다. `/feature-add`는 선택적인 명시 호출이다.
일반 구현·TDD는 선택된 방법론 하나로 수행한다. Superpowers를 사용 중이면 이 계약을 그 작업에
연결하고 RED→GREEN·설계·승인 루프를 별도로 반복하지 않는다. 미설치면 native 방식으로 수행한다.

## 시작 조건

1. 실제 제품 루트·AGENTS.md·관련 stack rule·승인된 요구·현재 변경을 읽는다. 제품의 테스트·품질·빌드
   명령과 직접 소비자, 관련 로드맵·체크리스트·사용 안내를 확인한다. 존재하지 않는 경로를 추측하지 않는다.
2. 기존 계획과 승인을 재사용한다. 실질적인 미결정이 있으면 `plan` 계약으로 필요한 부분만 정리한다.
   이미 구현된 동작의 변경은 `feature-modify`를 따른다.
3. 제품 Git 규약에 따라 기존 작업 브랜치에서 이어가거나 새 브랜치를 만든다. GitHub 하네스의
   `feature/<name>` 생성에는 승인된 `docs/specs/<name>.md`가 선행한다. 파일 존재는 승인 증거가 아니다.
   명시적 trivial 면제는 실제 자명한 변경에만 사용한다. 다른 사람의 변경을 stash·되돌리거나 덮어쓰지 않는다.
4. 로컬 전용 제품은 제품의 Git·검사 규칙을 따른다. 이 계약이 원격·공개·PR·배포 권한을 만들지 않는다.

## 구현에 연결할 계약

- 관련 표준과 설치된 API를 먼저 확인한다. 외부 입력·인가·오류 응답·연관 상태·DB 변경 등 실제로
  영향을 받는 경계의 정상·실패·경계 조건을 수용 기준과 검사에 연결한다.
- 동작 로직은 공개 결과를 단언하는 테스트를 먼저 작성한다. 원래 요구 미구현으로 실패하는 RED인지
  현재 담당자가 검수한 뒤 구현한다. import·문법 오류나 구현을 그대로 베낀 테스트는 RED 증거가 아니다.
- 검수한 수용 기준·spec/test를 구현 중 잠근다. 구현자는 테스트를 수정·삭제·약화·skip하지 않는다.
  계약 자체가 잘못됐다면 근거를 보고하고 계약 소유자가 원래 요구에 대조해 정정한 뒤 다시 검수한다.
- 문서·설정·순수 비주얼은 적합한 내용/구문/연결/화면 검사로 검증한다. 의미 없는 단위 테스트나
  수용 기준과 관계없는 E2E를 개수에 맞춰 추가하지 않는다. 필요한 접근성·디자인 검사는 별도로 연결한다.
- 단순 작업은 직접 수행한다. 위임이 유효하고 허용됐을 때만 소유 파일·잠긴 계약·검사·중단 조건을
  전달한다. 위임자는 다른 작업자의 변경을 보존하고, 독립 검증자는 구현에 참여하지 않는다.
- GREEN 뒤 변경 범위에서 필요한 정리만 한다. 실패 재시도는 새 증거나 바뀐 가설이 있어야 하며,
  해결되지 않는 실패에 패치를 쌓거나 환경 문제를 모델 변경으로 해결하려 하지 않는다.

## 완료와 인계

현재 담당자가 다음을 확인한다. 방법론에서 이미 얻은 결과는 현재 후보·관련 환경·범위에 맞으면 재사용한다.

- 수용 기준별 정상·실패·경계 검사와 제품이 요구하는 전체 품질 검사 통과
- 잠긴 spec/test 보존, 요청 밖 변경·불필요한 생성물·시크릿 없음
- 제품 정책·위험에 따른 필수 독립 검증 및 남은 제약 기록
- 관련 로드맵·체크리스트·진행·사용 문서 현행화

증거 판정은 `verification-before-completion`을 따른다. 변경·드리프트·새 실패·미해결 우려 또는
CI/리뷰의 신선도 조건이 있으면 해당 검사를 다시 실행한다. 실패·미확인은 완료로 보고하지 않는다.
승인된 Git 범위에서 제품 커밋 규약으로 변경을 기록한다. PR·머지는 별도 delivery 단계이며,
승인돼 있으면 `feature-merge`로 이어가되 리뷰·CI·사람 승인 요건을 그대로 적용한다.
