# 여러 개발자가 Team Harness로 함께 일하기

각 개발자는 자기 AI 대화와 작업공간에서 일하고, 요구·계약·진행은 제품의 같은 이슈나 문서로 공유한다.
한 대화가 팀 전체의 원본을 대신하지 않는다. 팀원에게 넘길 요청과 결과도 그 기록에 연결한다.
공통 셋업·검사 연결·브랜치·병합·출시 기준은 [개발 가이드](solo-development.md#개발자가-하는-일)를 따른다.

의존 PR은 [층별 개발 안내](stacked-development.md)를 함께 읽고 각 층·worktree의 writer와 통합 책임을 정한다.

## 처음 함께 사용할 때

각자 제품 저장소를 열고 아래 **첫 확인 요청**을 보낸다. 역할 이름은 예시이며 실제 분담으로 바꾼다.

```text
이 저장소에서 여러 개발자가 각자 AI와 Team Harness를 사용하려고 해.
역할은 A [API·데이터], B [화면], 통합 담당 [역할], 리뷰 담당 [역할]이야.
작은 팀에서는 역할을 겸할 수 있지만, 저장소가 요구하는 독립 리뷰와 사람 승인 조건은 유지해.
AGENTS.md, 기존 변경, 브랜치·작업공간, 로컬 검사·CI, Harness 적용 상태를 확인해줘.
공유 요구·계약·진행 기록의 위치와 담당 파일·의존 순서·통합 검증 책임이 정해졌는지 확인해.
기존 설정·다른 사람의 작업·승인 정책을 보존하고, 이미 연결된 구성은 재사용해.
아직 파일·설정·원격 정책을 변경하거나 팀원에게 메시지를 보내지 마.
지금 함께 시작 가능한지, 빠진 필수 준비와 실제 사용할 작업·리뷰·통합 흐름을 정리해줘.
확인과 미확인을 구분하고 전체 템플릿이나 Git Flow를 일괄 적용하지 마.
```

**첫 확인 완료 기준:** 각자 적용 상태와 공유 기록·담당 범위·의존 관계·검사·리뷰·통합 책임을 찾을 수 있다.
준비가 빠졌다면 대상·이유·필요한 변경을 정리하고, 그 범위를 정해 따로 맡긴다. 준비된 항목은 반복하지 않는다.
팀마다 사람 승인 수를 새로 강제하지 않고 기존 저장소 조건을 따른다.

## 공유 업무와 담당자별 시작

같은 주문 취소를 A(API·재고)와 B(화면·통합 확인)가 맡는 예다. 둘이 각자 AI를 사용해도 제품의
공유 계약과 기록은 하나로 연결한다. 인프라 변경이 없다면 인프라 담당이나 별도 역할 체계를 만들지 않는다.

```text
주문 취소의 API·재고 처리는 A, 화면은 B가 맡아. 두 작업의 응답·오류·상태 계약과
전체 완료 기준을 같은 이슈에 정리하고 담당 파일·의존 순서를 연결해줘. 아직 구현하지 마.
```

계약이 정해지면 각자 제품 저장소의 별도 브랜치·작업공간과 AI 대화에서 아래 요청을 보낸다.
대괄호를 실제 역할·파일·계약 위치로 바꾼다. 예시 A는 API·재고, B는 화면·통합 확인을 맡는다.

```text
공유 업무 계약 [이슈 또는 문서]에서 내 담당 [역할·파일]을 구현해줘.
목표·유지할 것·완료 기준은 그 계약을 따르고, 제품 검사·독립 리뷰·PR 생성까지 진행해.
다른 담당자의 변경을 보존해. 의존 작업이 미완료면 실제 연결과 대역 사용을 구분해 보고해.
계약 변경이 필요하면 같은 기록에 영향과 이유를 남기고 관련 담당자와 합의할 사항을 알려줘.
병합·배포는 별도로 요청할게. 실행하지 못한 필수 검사는 완료로 처리하지 마.
```

| 단계 | 할 일 | 단계별 완료 기준 |
| --- | --- | --- |
| 공유 계약 | 취소 상태·요청/응답·오류·재고 불변식을 합의 | A/B의 검사에 같은 업무 규칙을 사용하며 미결정과 범위가 표시됨 |
| 작업 분리 | 각자 브랜치·작업공간에서 담당 범위를 구현 | 파일 소유와 의존 순서가 명확하고 다른 사람의 변경을 보존; 담당 검사 통과 |
| 개별 PR | 독립 AI 리뷰와 동료의 제품 관점 리뷰를 연결 | 현재 후보의 지적 처리·CI 성공, 저장소가 요구하는 사람 승인·CODEOWNERS 충족 |
| 합친 상태 검증 | 실제 API·데이터와 화면을 연결해 실행 | 화면 취소→주문/재고 저장→재조회·새로고침 유지, 거부 응답 표시까지 통과 |
| 병합·출시 | 선택한 main 중심 또는 Git Flow로 전달 | 원격 병합·검사 후보 일치, 요청된 출시/배포 단계만 실제 증거로 확인 |
| 인계 | 다음 담당자가 같은 제품 기록에서 재개 | 아래 인계 요청으로 현재 상태와 남은 실행을 확인할 수 있음 |

통합 담당자는 두 PR의 결합 후보와 검사 범위를 정하고, 리뷰어는 현재 head/base와 공유 계약을 검토한다.
두 PR이 각각 통과했어도 합친 기능은 별도로 확인한다. API 대역을 쓴 화면 개발은 실제 연결 완료와
구분한다. 사람 승인과 보호는 [기존 리뷰 기준](../code-review.md)을 따르며 동료 부재를 solo 예외로 처리하지 않는다.
복잡한 영역 인계·중단 뒤 재개는 `ao-coordinate`를 연결하고 단순 수정은 해당 작업에서 바로 처리한다.

```text
합친 후보에서 실제 API·데이터로 화면 취소, 주문·재고 저장, 재조회·새로고침, 거부 표시를 확인해줘.
운영과 분리된 승인 환경을 사용하고 미실행은 완료로 처리하지 마.
```

```text
현재 후보 SHA와 변경 이유, 실행한 검사·결과·환경, 미해결 항목·다음 행동을 이 이슈에 정리해줘.
다음 담당자는 현재 원본과 증거를 대조하고, 후보·환경·검사 범위가 같은 결과는 재사용해.
실행하지 못한 필수 검사는 미확인으로 유지하고 남은 승인 범위만 이어서 진행해.
```

## 기능 개발 외 업무도 같은 방식으로

설계는 공유 결정과 영향 범위, 진단은 재현·원인·미확인 가설, 유지보수는 변경·유지 검사를 같은 기록에 남긴다.
[업무별 요청 예시](solo-development.md#기능-개발-외-업무)에서 진행 범위와 완료 기준만 바꾼다.
진단 담당자가 수정 담당자에게 넘길 때도 위 인계 요청을 쓴다. 진단·설계만 요청했으면 구현으로 이어가지 않는다.

이 문서의 역할과 요청은 사용 예시다. 실제 팀 참여·제품 실행·회사 도입의 검증 결과를 뜻하지 않는다.
