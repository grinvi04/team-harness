# systematic-debugging — 프로젝트 진단·수정 인계 계약

사용자는 오류나 증상을 자연어로 설명한다. 일반 디버깅은 선택된 방법론 하나를 따른다.
Superpowers 진단을 진행 중이면 그 재현·가설 판별 결과에 아래 계약을 연결한다. 같은 진단을 다시
시작하지 않는다. 미설치면 native 방식으로 재현·사실·가설의 판별 증거를 수집한다.

## 권한과 원본

- 제품 AGENTS.md·관련 stack rule에서 실제 검사 명령을 읽고 현재 작업트리·후보·관련 환경을 확인한다.
- **진단 전용 요청은 파일을 수정하지 않는다.** 브랜치·커밋·PR도 만들지 않는다.
- 수정 요청도 근본 원인을 확정하기 전에는 코드를 수정하지 않는다. 진단 결과가 수정 권한을 새로 만들지 않는다.
- 관련 없는 미커밋 변경은 보존한다. 수정이 그 변경과 충돌하면 중단하고 범위를 확인하며 임의 stash·
  되돌리기·브랜치 전환을 하지 않는다. 영향 없는 읽기 전용 조사는 이어갈 수 있다.
- 운영 DB·운영 인프라 변경, 파괴적 시험, 시크릿 출력은 진단 증거로 사용하지 않는다.

## 프로젝트가 받아야 할 증거

- 기대 동작과 실제 동작, 최초 실패 경계
- 현재 후보·입력·환경, 재현 명령·종료 코드와 반복/간헐 조건
- 관찰한 사실과 아직 미확정인 추론의 구분
- 원인 가설과 이를 구별하는 판별 실험, 확인/기각 결과
- 확정한 원인의 인과 경로와 최소 수정 범위, 또는 미확정 이유·다음 관측

설치된 API·로그·fixture가 실제 경계를 나타내는지 확인한다. 원인을 확정하지 못하면 미확정으로 보고하고 추측으로 수정하지 않는다. 같은 실패는 새 증거나 바뀐 가설 없이 반복하지 않는다.

## 수정으로 인계

원인을 확인했고 수정이 승인된 경우에만 `feature-modify`의 변경·유지 테스트 계약으로 이어간다.
공개 동작에는 자동 회귀 테스트, CI·빌드·설정에는 적합한 실행 가능 검사를 사용하고 수정 전 RED를
확인한다. 구현 중 계약을 잠그며 테스트 삭제·약화·skip으로 통과시키지 않는다.
현재 방법론에서 이미 검수한 재현·RED를 중복 작성하지 않는다.

원래 증상과 회귀 검사를 통과하고 제품의 전체 품질 명령·필수 독립 검증·문서 현행화를 확인한다.
`verification-before-completion`에 따라 현재 후보·환경·범위가 동일한 증거를 재사용하고 달라진 부분은
다시 확인한다. 결과에는 원인/미확정 사유·검사 결과·변경 범위·남은 한계를 남긴다.
진단 완료와 수정 완료, 로컬 구현과 PR/릴리즈 상태를 구분한다.
