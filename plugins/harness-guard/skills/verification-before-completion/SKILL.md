# /verification-before-completion — 완료 주장 전 증거 게이트

“될 것이다”와 “현재 됐다”를 구분한다. 완료라는 말보다 먼저, **바로 지금의 상태를 증명하는 증거**를 수집한다.

일반 방법론에서 수행한 검사를 현재 프로젝트의 완료 조건에 연결한다. 이미 같은 후보·관련 환경·검사
범위를 검증했다면 원본 결과를 재사용하고 별도 검사 루프나 승인 절차를 시작하지 않는다.

## 완료 기준

1. 검증할 주장을 관찰 가능한 증거와 1:1로 매핑한다.
2. 현재 작업트리와, 변경이 커밋됐다면 정확한 HEAD SHA를 기준으로 유효한 증거를 확인한다.
3. 각 항목을 `PASS / FAIL / UNVERIFIED / SKIP`으로 판정하고 명령·종료 코드·대상 SHA를 남긴다.
4. 필수 항목에 `FAIL`이나 `UNVERIFIED`가 하나라도 있으면 완료로 판정하지 않는다.

## Phase 0 — 호출 맥락과 권한 고정

1. repo의 `AGENTS.md`와 작업 대상 stack rule에서 테스트·빌드·품질 명령을 읽는다.
2. 호출 맥락을 구분한다.
   - **상위 workflow에서 호출:** 검증 결과만 돌려준다. 호출 workflow가 최종 판정을 소유한다.
   - **직접 호출:** 확인·검증 결과만 보고한다. 실패나 미확인이면 파일을 수정하지 않고 보고 후 중단한다.
3. 이 스킬은 수정·커밋·PR·머지·릴리즈 권한을 새로 만들지 않는다. 실패 수정은 사용자가 맡긴 기존 workflow의 범위에서만 수행한다.
4. 대상 repo·허용된 변경·관찰만 할 소비자를 기존 작업 기록에 짧게 고정한다. 발견 결함의 중요도나
   짧은 “계속”을 근거로 보류된 다른 프로젝트 수정·배포를 재개하지 않는다. 범위 밖 발견은 증거와
   후속 조건으로 남기고 승인된 현재 작업을 계속한다.
5. 운영 DB나 운영 인프라를 변경하지 않는다. destructive probe나 실제 고객 요청 생성도 완료 증거로 사용하지 않는다.

## Phase 1 — 주장을 증거 계획으로 변환

모호한 완료 주장을 관찰 가능한 증거로 바꾼다.

### QA 범위와 항목별 완료 기준

상태/관계 이동·캐시·비동기·인증/권한·fixture 환경이 관련되면 [위험별 관찰 경계](risk-boundaries.md)를
읽고 해당 행을 아래 범위표에 연결한다. 작은 문구 수정 등 무관한 변경에는 로딩·전수 시험을 요구하지 않는다.
기대 결과의 근거가 불명확하거나 조합·행동 순서·미지 증상·불안정 시험·시험 검출력이 쟁점이면
[시험 설계와 판정자](test-design.md)에서 해당 항목만 선택한다. 기존 범위표를 재사용한다.

구현·시험 전에 원래 요구와 제품의 지원 환경에서 범위를 정한다. 기존 스펙·이슈·검증 기록 하나를
사용하며 작은 수정은 짧은 목록으로 충분하다. 완료 직전에 호출됐다면 기존 범위의 누락부터 대조한다.

- **선정 근거:** 요구사항·사용자 흐름 → 변경 경계와 직접 소비자 → 실패 시 영향 순서로 연결한다.
  이미 있는 테스트나 구현자가 고친 파일 목록만으로 범위를 정하지 않는다. 기능·데이터 정합성·오류 복구·
  UI/접근성·성능·보안 중 관련 축을 고르고, 비적용 축·제외 환경은 근거를 남긴다. 모든 축의 전수 검사를
  매번 강제하지 않으며 새 반례가 나오면 관련 경계만 보완한다.
- **필수 범위:** 요청한 수용 기준, 원래 재현, 변경에 노출된 핵심 흐름과 데이터 손실·중복·권한 침해
  위험, 제품의 필수 품질 gate를 포함한다. 직접 소비자의 유지 동작도 확인한다. 정상·실패·경계 조건과
  지원 브라우저·화면·입력·데이터·상태 조합에서 위험을 대표하는 사례 및 그 선택 이유를 남긴다.
- **판정 기준:** 실행 전에 아래 항목을 채운다. 기대 결과는 화면·API·저장 상태 등 관찰 대상과 정확한
  값/불변식으로 쓴다. 성능·접근성 같은 품질 기준은 제품이 채택한 기준과 임계값을 연결한다. 기준이
  없으면 근거 있는 제안을 명시하고, 수용 기준을 바꾸는 선택만 확인한다. 테스트 개수나 커버리지 수치만으로
  충분성을 판정하지 않는다.
- **판정자·진입 조건:** 기대값의 출처(업무 규칙·수용 예제·독립 계산)를 연결한다. 구현의 결과를 그대로
  정답으로 복사하지 않는다. 지원 실행 환경·격리 데이터·필수 의존성이 준비되지 않았으면 해당 항목은
  UNVERIFIED이며, 필요한 준비와 영향받지 않는 검사를 구분한다.

| 요구·위험 / 선정 이유 | 조건·행동 / 환경 | 기대 결과·품질 기준 | 방법·관찰 경계 | 필수 여부 | 증거·판정 |
|---|---|---|---|---|---|
| 예: 응답 유실 뒤 등록 재시도 시 중복 위험 | 격리 DB에 저장 성공 후 응답 차단, 같은 요청 재시도·새로고침 | 같은 논리 요청의 저장 레코드와 화면 항목 각각 1개, 후속 수정 보존 | 실제 API·DB 통합 검사 + 브라우저 흐름 | 필수 | 실행 전 UNVERIFIED, 실행 후 후보·결과 연결 |

예시는 멱등 등록 요구가 있는 제품에 적용한다. 구체적인 키 설계·DB·테스트 코드는 제품이 소유한다.
목 응답·렌더 스모크는 그 관찰 경계만 증명한다. 저장·복구가 요구라면 안전한 격리 환경에서 실제 저장
경계와 소비자 결과를 확인하며, 모든 외부 서비스를 운영 환경으로 호출하라는 뜻은 아니다.

**완료 조건:** 필수 항목 모두 PASS, 범위 안 미해결 차단 결함 0, 제품 필수 gate 통과, 현재 후보와
증거 일치가 함께 필요하다. 비필수 잔여 항목은 영향·제외 근거·후속 행동을 보고한다. 접근 불가·시간 부족·
도구 미설치는 UNVERIFIED이며 SKIP이 아니다. SKIP은 실제 비적용만 허용한다. 실패 뒤 필수 항목을
비필수로 내려 통과시키지 않는다. 범위·수용 기준 변경은 원래 요구와 대조하고 필요한 승인을 받는다.
조사 범위를 마쳤다는 사실을 제품 전체의 무결함이나 재현하지 못한 원래 문제의 해결로 확대하지 않는다.

| 주장 | 우선 증거 |
|---|---|
| 버그가 해결됨 | 원래 재현 명령 + 잠긴 회귀 검사 |
| 기능이 동작함 | 수용기준별 대상 테스트 + 핵심 e2e |
| 회귀가 없음 | `AGENTS.md` 전체 품질 명령 |
| 변경 범위가 정확함 | `git diff --check` + stat + 전체 diff |
| PR·머지 준비 완료 | 현재 HEAD와 PR head SHA 일치 + required CI·리뷰·mergeability |
| 릴리즈·배포 준비 완료 | release gate + 배포 대상 SHA 일치 + 읽기 전용 health 상태 |
| 문서·설정 완료 | 구문·링크·소비자 경로 검사 + 관련 로드맵·체크리스트·진행 상태를 실제 변경·검사·미해결 항목과 대조 |

- 검증 대상이 없는 항목을 억지 명령으로 꾸미지 않는다. 적용 불가 항목은 `SKIP`으로 표시하고 이유를 쓴다.
- “테스트 통과”처럼 범위가 불명확하면 대상 테스트인지 전체 품질인지 먼저 구체화한다.

## Phase 2 — 현재 상태의 새 증거 수집

1. `git status --short --branch`로 현재 작업트리 상태를 기록한다.
2. 커밋된 변경이면 `git rev-parse HEAD`로 HEAD SHA를 기록한다. 미커밋 변경은 SHA가 증명하지 못하므로 diff를 별도 증거로 취급한다.
3. 부족한 증거만 검증 명령·종료 코드를 새로 수집하고 핵심 출력을 기록한다. 기존 실행의 대상 파일·
   관련 환경·검사 범위를 현재 원본과 대조해 같으면 재사용한다. 변경·드리프트·새 실패·미해결 우려나
   gate의 신선도 조건이 있으면 영향을 받는 검사를 다시 수행한다. 이전 세션의 기억이나 오래된 로그만으로 판정하지 않는다.
4. CI와 배포 증거는 reported SHA가 현재 HEAD와 일치하는지 확인한다. 다른 commit·branch의 green 결과는 현재 변경의 증거가 아니다.
5. 외부 상태를 읽을 수 없으면 성공으로 추정하지 말고 `UNVERIFIED`로 둔다.

## Phase 3 — 증거 자체를 반증

PASS를 선언하기 전에 false positive 가능성을 공격한다.

- 대상 테스트가 실제 변경 동작을 단언하는지 확인한다. 존재·truthy만 보는 약한 테스트나 구현을 그대로 베낀 테스트는 증거로 부족하다.
- 버그 수정은 가능하면 수정 전 RED가 원래 증상 때문에 실패했다는 기록을 대조한다.
- guard·차단·권한처럼 거부가 본질이면 허용 사례만 보지 말고 안전한 반례·우회 입력을 시험한다.
- 전체 품질 명령이 실패 테스트를 skip하거나 다른 디렉터리만 검사하지 않는지 확인한다.
- 요구에서 고른 QA 범위와 실행된 사례를 대조한다. 모든 테스트가 green이어도 필수 흐름·관찰 경계가
  빠졌으면 UNVERIFIED다. 결함이 존재할 때도 통과할 단언인지 반례로 검토한다.
- 최초 실패·재시도 결과와 조건을 함께 보존한다. 재시도만 성공한 필수 flaky를 그대로 PASS로 바꾸지 않는다.
  원인과 환경 회복/수정의 증거로 해소하며, 미해결이면 FAIL 또는 UNVERIFIED다. 격리·skip으로 필수 범위를 없애지 않는다.
- diff에 요청 밖 파일, 테스트 약화, 생성물, 시크릿이 섞이지 않았는지 확인한다.
- 관련 진행 문서의 완료·미완료·차단·다음 행동이 실제 후보와 맞는지 확인한다. 파일 존재나 링크 정상만으로
  현행화를 통과시키지 않는다. 구현·검증·병합·릴리즈·설치 상태를 구분하고 취소한 작업이 다음 할 일로 남았는지 본다.

반증을 위해 테스트를 수정하거나 운영 상태를 바꾸지 않는다.

## Phase 4 — 선택적 독립 검증

제품 정책이 요구하는 독립 검증은 필수다. 그 외 위험이 크거나 판단이 갈리는 주장은 verifier에 선택적 독립 반증을 맡긴다.

- verifier에는 현재 주장, raw diff, 명령 결과처럼 원본 증거를 제공한다. 기대 결론을 주입하지 않는다.
- verifier는 증거 수집과 반증만 한다. verifier가 파일을 수정·커밋·머지하지 않으며 완료 판정을 대신하지 않는다.
- 독립 검증 결과가 충돌하면 현재 호출 workflow가 차이를 해소할 때까지 `UNVERIFIED`로 둔다.

## Phase 5 — fail-closed 판정

| 상태 | 의미 | 완료 주장 가능 여부 |
|---|---|---|
| PASS | 현재 상태를 직접 증명함 | 모든 필수 항목 PASS일 때만 가능 |
| FAIL | 명령 실패 또는 반례 발견 | 불가 |
| UNVERIFIED | 실행 못 함, 증거가 stale·불충분·다른 SHA | 불가 |
| SKIP | 실제로 적용 불가하며 이유 기록 | 다른 필수 항목으로 판정 |

필수 항목의 실패나 미확인이 있으면 완료로 판정하지 않는다. 상위 workflow 호출이면 실패 증거와 함께 해당 단계로 돌려보내고, 직접 호출이면 무수정 상태로 보고하고 중단한다.

## 결과 보고

다음 표를 사용한다.

| 주장 | 증거 명령·대상 | 결과 | 판정 |
|---|---|---|---|
| 예: 회귀 없음 | `test-command` (worktree/HEAD SHA) | exit 0/1 + 핵심 출력 | PASS/FAIL |

선정한 QA 범위·항목별 기준과 위 증거를 연결하고 누락·제외·미확인 및 잔여 결함을 함께 보고한다.
실행 중인 앱을 확인했다면 그 앱의 후보·환경도 구분한다. 로컬 검사 통과만으로 실행 중인 앱 반영을 주장하지 않는다.
마지막에 해당 범위의 전체 판정(`VERIFIED` 또는 `NOT VERIFIED`)과 아직 확인하지 못한 한계를 명시한다. 실행하지 않은 항목을 실행한 것처럼 말하지 않는다.
