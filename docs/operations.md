# 운영 표준 — 장애 대응·로깅·릴리즈

[표준 적용 기준](standards-scope.md)을 따른다. 운영 서비스의 실패 영향과 실제 지원 체계에 맞춰 적용한다.
로그·진단 경로는 개발 중에도 필요하다. 특정 업무·클라우드·팀 규모를 전제로 하지 않는다.

## 1. 장애 대응

### 장애 등급

등급·응답 시간은 제품의 지원 약속과 실패 영향으로 정한다. 아래는 조정 가능한 예시다.

| 등급 | 정의 | 초동 대응 | 예 |
|---|---|---|---|
| **SEV1** | 핵심 서비스 중단, 데이터 손상·유출 | 즉시, 전원 가용 인력 | 인증 전면 장애, 데이터 손상 |
| **SEV2** | 핵심 기능 장애 (우회로 존재) | 1시간 내 | 주요 기능 실패(대체 경로 존재) |
| **SEV3** | 부분 기능·성능 저하 | 1영업일 내 | 일부 조회 지연 |

판단이 애매하면 **한 등급 위로** 선언하고 나중에 낮춘다.

### 대응 절차

1. **감지**: 채택한 관측 도구와 신고 경로로 장애를 확인한다
2. **선언**: 발견자가 등급 선언 + 스레드 생성. SEV1/2는 리드 즉시 호출
3. **역할 분리** (SEV1/2): **지휘자(IC)** 1명 — 전파·의사결정·타임라인 기록 전담, 조치는 하지 않는다 /
   **조치자** — 복구 작업 전담. 가용 인원에 맞춰 역할을 정하고 조치·판단 기록을 남긴다
4. **복구 경로 선택**: 롤백 후보와 현재 DB·데이터·외부 상태의 호환성을 먼저 확인한다.
   Git revert가 DB나 배포를 자동 복구하지 않는다. 롤백·보정·기능 제한 중 피해가 작은 경로를 선택한다.
5. **권한 유지**: 장애 선언만으로 운영 조작 권한을 얻지 않는다. 승인된 대응 절차 안에서 조치한다.
   수동 변경은 기록하고 종료 후 코드·설정·마이그레이션의 현재 상태와 맞춘다.
6. **종료 선언**: IC가 복구 확인 후 채널에 명시적 종료 + 영향 범위 1차 공유

### 포스트모템

회고 대상·기한은 프로젝트에서 정한다. [Google SRE의 회고 안내](https://sre.google/workbook/postmortem-culture/)를 참고한다.

**Blameless 원칙** — 사람의 실수는 시스템(가드·절차·도구)의 결함으로 기술한다.
"왜 A가 실수했나"가 아니라 "왜 시스템이 그 실수를 허용했나".

템플릿: 요약(영향 범위·지속 시간) / 타임라인(감지~복구) / 근본 원인(5 whys) /
잘된 점·운이 좋았던 점 / **재발 방지 액션** — 프로젝트의 이슈에 담당·기한·완료 조건 기록

시험에서 놓친 결함이면 그 액션에 누락된 요구·조합·관찰 경계와 회귀 검사를 연결한다.
가능한 격리 환경에서 동일 검사가 결함 후보를 거부하고 수정 후보를 통과시키는지 확인한다.
회고 작성·시험 개수 증가만으로 재발 방지 완료를 판정하지 않으며, 운영 재현·장애 주입 권한을 새로 만들지 않는다.
(액션 없는 포스트모템은 작성하지 않은 것과 같다)

### 시크릿 유출 대응 런북

시크릿 유출은 **SEV1**로 선언하고 §1의 IC/조치자 분리를 따른다. **값 폐기·회전이 히스토리 purge보다 우선**이다. 대응 실행 전에 [전체 런북](operations-secret-response.md)을 읽는다.
main/develop force-push는 별도 소유자 승인과 보호 변경·복원 절차가 필요하다. `solo-merge`는 리뷰 승인 요건만 다루며 force-push를 허용하지 않는다.

## 2. 온콜 (서비스 오픈 후)

- 대응 담당·백업·운영 시간을 실제 지원 약속과 가용 인원에 맞춰 정한다.
- 알람 정책: **알람 = 사람이 조치해야 하는 것만.** 조치 불가능한 알람은 만들지 않고,
  무시되는 알람은 원인·임계값·대응 가능성을 검토하고 조정한다.

## 3. 로깅 실무 (첫 코드부터 적용)

### 레벨 기준

| 레벨 | 기준 | 예 |
|---|---|---|
| `ERROR` | 요청·작업의 실패 — 알람 기준은 영향·빈도로 별도 정의 | 결제 연동 실패, 미처리 예외 |
| `WARN` | 잠재 문제·자동 복구된 이상 | 재시도 후 성공, 응답 지연 임계 초과 |
| `INFO` | 업무 이벤트·상태 전이 | 리소스 생성·상태 변경, 배치 시작·종료(건수 포함) |
| `DEBUG` | 개발 진단용 — **운영 기본 off** | 쿼리 파라미터, 분기 추적 |

- 사용자 입력 오류(검증 실패 400)는 ERROR가 아니다 — INFO/WARN
- 루프 내부 INFO 금지 (배치는 시작·종료·집계만)

### 구조화 필드 표준 (JSON 예시)

```json
{
  "timestamp": "...", "level": "INFO", "service": "api",
  "traceId": "4bf92f35...", "userId": 123,
  "event": "RESOURCE_UPDATED", "message": "리소스 수정",
  "resourceId": "res_001"
}
```

- 업무 이벤트는 `event` 코드(SCREAMING_SNAKE)를 붙인다 — 메시지 문자열 검색이 아니라 코드로 집계
- **개인정보·시크릿 출력 금지** (`auth-standards.md`) — 마스킹 유틸 공통 제공

### Trace ID 전파

[W3C Trace Context](https://www.w3.org/TR/trace-context/)의 형식을 사용한다면 지원 라이브러리와 전파 경로를 확인한다.

- 표준: **W3C Trace Context** (`traceparent` 헤더) — 서비스 간 호출 시 자동 전파 (미니서비스 대비)
- 추적을 채택하면 호출·로그에 연결하고 비동기 작업에서도 전파되는지 확인한다.
- 문의용 식별자를 응답에 제공한다면 노출 범위와 헤더 계약을 정한다.
- 프론트 오류를 연결할 때 채택한 수집 도구·식별자 계약을 따른다.

### 보존

- 보존 기간은 민감도·조회 목적·비용·제품 요구에 맞춰 정한다. 감사 이력과 진단 로그를 구분한다.

### 하네스 자체 감사 로그

위는 **앱**의 로깅. 하네스(harness-guard)도 게이트 결정을 로컬 로그로 남긴다 — 실측·감사용:

| 로그 | 위치 | 내용 |
|---|---|---|
| 가드 차단 | `~/.claude/hooks/guard-block.log` | deny된 명령·사유·session·cwd (시크릿 마스킹) |
| Codex 가드 차단 | `~/.codex/hooks/guard-block.log` | Codex wrapper에서 deny된 명령·사유·session·cwd (Claude 로그와 격리) |
| 모델 티어링 | `~/.claude/hooks/subagent-model.log` | 실행된 hook의 모델·effort 선택/skip 기록; 실제 플랫폼 적용값은 별도 확인 |

- **읽는 법**: `grep 'cwd=.*/<repo>' ~/.claude/hooks/subagent-model.log`(특정 repo 스폰 모델 감사) · `grep DENY ~/.claude/hooks/guard-block.log`(차단 이력).
- **VCS 밖**: 머신 로컬 런타임 데이터(cwd·명령 히스토리 포함)라 **repo에 커밋하지 않는다** — 소스(훅)만 versioned. 팀 집계가 필요하면 로컬 커밋이 아니라 중앙 스토어로 ship.
- **로테이션**: 256KB 초과 시 훅이 최근 절반만 보존(무한 증가 방지).

## 4. 릴리즈·버전 정책

SemVer를 채택했다면 공개 계약의 호환성으로 버전을 정한다.
아래 생성 명령과 태그 절차는 Team Harness 자체의 운영 방식이다. 소비 제품은 실제 도구를 연결한다.
- **CHANGELOG 자동 생성**: Conventional Commits 기반 (`node scripts/generate-changelog.mjs`) — 수기 작성 금지.
  `feat`/`fix`만 노출, 커밋 메시지 품질이 곧 릴리즈 노트 품질 (`code-review.md`).
  정식 태그 전에는 `node scripts/generate-changelog.mjs --release vX.Y.Z`로 현재 `HEAD`의 release
  candidate를 생성하며, `/release` Phase 1에서 이 결과를 커밋한다.
- **두 종류의 릴리즈 노트**: 개발용 = CHANGELOG / **사용자 공지용** = 업무 영향 중심 한국어 별도 작성
  ("주문 화면에서 ~가 가능해집니다") — 기술 용어 금지
- 공지 대상·채널·시간은 프로젝트의 지원 약속과 배포 영향에 맞춰 정한다. 외부 메시지는 승인 범위 안에서 보낸다.

## 6. 배포 검증·헬스체크

> **`/release` Phase 0(스테이징)·Phase 5(운영)가 이 절차를 따른다.** 명령·URL은 각 repo의
> `AGENTS.md`에서 읽으므로, **모든 배포 대상 repo는 AGENTS.md에 실제 도메인·헬스 엔드포인트를
> 명시**한다(플레이스홀더 `<...>` 금지 — 정의 없으면 Phase 5가 못 돈다).

### 원칙: liveness ≠ freshness

헬스 URL의 성공 응답은 그 요청의 성공이다. 최신 후보 배포·권한·DB·업무 동작 전체의 증거는 아니다.
배포 결과의 commit 또는 이미지 digest가 승인된 후보와 맞는지 확인한다.
관련 DB·연동·핵심 기능은 별도의 안전한 검사로 확인하고 실행하지 못한 범위는 미확인으로 남긴다.

### 층별 검증

| 층 | 확인할 것 |
|---|---|
| 응답 | 프로젝트의 실제 헬스 경로와 기대 응답 |
| 배포 후보 | 플랫폼이 보고한 버전·commit·digest와 승인 후보 |
| 의존 서비스 | 연결 상태와 필요한 최소 동작; 상태 목록만으로 업무 정상 판정 금지 |
| 실패 원인 | 로그·권한·연결 브랜치·환경 키·쿼터·웹훅 상태 |

### 운용 규칙

변수의 이름·범위·주입 시점을 코드와 배포 안내에서 대조한다. 비밀 값은 출력하지 않는다.
특정 서비스의 CLI·계정·환경 이름은 프로젝트 런북에 둔다.
배포 실패를 진단할 때 배포 명령을 자동 실행하거나 다른 계정·요금제로 바꾸지 않는다.
AI는 운영 배포를 임의 실행하지 않는다. 기존 권한과 사용자 승인 범위를 따른다.
